GPU 메모리와 모델 크기의 관계

VRAM은 가중치, KV cache, 그 밖의 오버헤드 세 덩어리로 나뉩니다. 첫 번째만 계산하면 반드시 틀립니다.

쉽게 말하면 · GPU 메모리는 책상이다

GPU 메모리(VRAM)를 책상이라고 생각해 보세요. 이 책상 위에 세 가지를 올려야 합니다.

덩어리비유하는 일
가중치두꺼운 백과사전모델이 배운 지식 그 자체
KV cache대화 메모장지금까지 나눈 대화를 적어 두는 공간
오버헤드필기도구, 스탠드프로그램이 돌아가는 데 필요한 잡다한 것 (2~4GB)

책상이 작으면 백과사전부터 안 올라가고(로딩 OOM), 백과사전은 올렸는데 메모장 놓을 자리가 없으면 사람을 받을 수 없습니다(KV 부족).

가중치: 파라미터 수 × 파라미터당 바이트

가중치 메모리 = 파라미터 수 × 바이트/파라미터
모델BF16 (2B)FP8 / INT8 (1B)INT4 (≈0.55B, 스케일 포함)
8B16 GB8 GB4.4 GB
32B64 GB32 GB17.6 GB
70B140 GB70 GB38.5 GB
405B810 GB405 GB223 GB

"70B"는 파라미터(모델이 학습한 숫자)가 700억(70 Billion) 개라는 뜻이고, 표 머리글의 2B·1B는 파라미터 하나가 차지하는 바이트입니다. 그래서 70B를 BF16으로 올리면 700억 × 2바이트 = 140GB, 가중치만 140GB입니다. 80GB 카드 한 장에는 처음부터 들어가지 않습니다. 설정을 잘못한 게 아니라 산수로 안 되는 상황이고, 이것이 가장 흔한 OOM의 정체입니다.

KV cache: 동시 요청과 컨텍스트 길이에 비례

KV cache를 이해하려면 모델이 어떻게 생겼는지 먼저 조금 알아야 합니다. ChatGPT, Llama, Claude, Qwen 등 지금 거의 모든 LLM은 Transformer라는 설계 구조를 씁니다. GPT의 T도 Transformer(Generative Pre-trained Transformer)이고, 2017년 Google 논문 "Attention Is All You Need"에서 처음 나왔습니다.

Transformer는 같은 모양의 층(레이어)을 수십 개 쌓은 구조입니다. Llama 3.1 70B는 80층입니다. 토큰이 아래층부터 차례로 올라가며 점점 깊이 이해되고, 맨 위층에서 다음에 올 토큰을 고릅니다. 각 층은 attention으로 앞에 나온 토큰 중 무엇을 참고할지 살피고, feed-forward로 그 내용을 가공합니다. attention은 도서관에서 자료를 찾는 방식과 비슷해서, 토큰마다 세 가지 값을 만들어 씁니다.

값도서관에 비유하면역할
Query내가 찾는 질문"지금 나는 이런 정보가 필요해"
Key책 등에 붙은 제목표"나는 이런 내용을 담고 있어"
Value책의 실제 내용찾았을 때 가져가는 정보

"철수는 사과를 샀다. 그는…"에서 "그는"을 처리할 때, "그는"의 Query를 앞 토큰들의 Key와 하나씩 맞춰 보면 "철수"가 가장 잘 맞습니다. 그래서 철수의 Value를 가져와 "그 = 철수"라고 이해합니다.

즉 새 토큰을 하나 만들 때마다 앞 토큰들의 Key와 Value가 전부 필요합니다. 매번 다시 계산하면 낭비이므로, Transformer는 이미 처리한 토큰의 Key·Value를 레이어마다 저장해 두고 재사용합니다. 이 저장 공간이 KV cache, 위 비유의 대화 메모장입니다. 80개 층이 각자 따로 Key·Value를 만들기 때문에 아래 식에 레이어 수가 곱해집니다. 그리고 대화가 길수록 메모장이 두꺼워지고 사용자가 많을수록 메모장 개수가 늘어나서, 전체 크기는 길이와 사용자 수에 비례해 커집니다.

토큰당 KV = 2(K,V) × 레이어 수 × KV 헤드 수 × 헤드 차원 × 바이트

Llama 3.1 70B(80 레이어, KV 헤드 8개, 헤드 차원 128, BF16)를 넣으면 토큰당 2×80×8×128×2 = 327,680 B, 약 0.33MB입니다.

위 식의 "KV 헤드 수"에는 설명이 하나 필요합니다. Llama 3.1 70B는 attention 헤드가 64개인데, KV 헤드는 8개뿐입니다. 요즘 모델 대부분이 쓰는 GQA(Grouped Query Attention) 때문입니다. Query 헤드 8개가 한 묶음이 되어 Key·Value 헤드 하나를 같이 쓰도록 설계해서, 품질은 거의 그대로 두고 KV cache를 1/8로 줄였습니다. 저장해야 하는 건 Query가 아니라 Key·Value이므로, 계산에는 KV 헤드 수가 들어갑니다.

자주 하는 실수

KV 헤드 자리에 num_attention_heads(70B는 64)를 넣으면 KV cache가 8배 크게 나옵니다. 반드시 num_key_value_heads를 넣습니다. 반대로 GQA를 쓰지 않는 옛 모델은 두 값이 같아서, 같은 크기라도 KV cache가 훨씬 큽니다.

70B, BF16 KV요청 1개동시 16개동시 64개
컨텍스트 4K1.3 GB21 GB86 GB
컨텍스트 8K2.7 GB43 GB172 GB
컨텍스트 32K10.7 GB172 GB687 GB

8K 대화 하나는 2.7GB지만 64명이 동시에 쓰면 172GB가 됩니다. 가중치가 겨우 들어가도 메모장 놓을 자리가 없으면 서비스가 되지 않습니다. 반대로 KV를 충분히 확보하는 것이 곧 동시 처리량입니다.

오버헤드: 잊기 쉬운 2~4GB

  • CUDA context: 프로세스가 GPU를 잡는 순간 0.5~1GB
  • 활성값(activation): prefill 중 중간 텐서. 긴 프롬프트를 한 번에 처리할수록 커짐
  • CUDA graph: vLLM이 decode 속도를 위해 미리 캡처하는 그래프, 수백 MB~수 GB
  • 다른 프로세스: 같은 GPU에 떠 있는 임베딩 서버, 주피터 커널 등. nvidia-smi로 먼저 확인

숫자를 어디서 찾고, 어떻게 확인하나

위 계산에 필요한 값은 Hugging Face 모델 저장소의 config.json에 다 있습니다. Llama 3.1 70B라면 이런 항목을 봅니다.

{
      "num_hidden_layers": 80,          // 레이어 수
      "num_attention_heads": 64,        // Query 헤드 수 (KV 계산에 넣으면 안 됨)
      "num_key_value_heads": 8,         // KV 헤드 수 (GQA)
      "hidden_size": 8192,              // head_dim = 8192 / 64 = 128
      "torch_dtype": "bfloat16"         // 파라미터당 2바이트
    }

파라미터 수는 모델 이름의 숫자(70B)가 아니라 모델 카드에 적힌 실제 값(70.6B 등)을 쓰는 게 정확합니다. 그리고 계산은 어디까지나 예측이라, 실제로 띄운 뒤 두 곳에서 맞춰 봅니다.

  • vLLM 기동 로그: 가중치가 차지한 메모리, KV cache로 잡힌 크기(토큰 수), 요청 길이 기준 최대 동시 처리 수가 찍힙니다. 계산값과 나란히 적어 두면 내 환경의 오버헤드가 얼마인지 거꾸로 알 수 있습니다.
  • nvidia-smi: 프로세스별 실제 사용량을 봅니다. vLLM은 예산만큼 미리 잡아 두므로 요청이 없어도 거의 꽉 찬 것처럼 보이는 게 정상입니다.
이 글의 단위

이 글은 GB(10억 바이트)로 계산합니다. GPU 용량(80GB)도 같은 GB로 보고 근사했습니다. vLLM 로그와 nvidia-smi는 GiB(1024³ 바이트)나 MiB로 찍기 때문에, 같은 값이 약 7% 작게 보입니다. 예를 들어 BF16 70B의 가중치 140GB는 약 130GiB입니다.

Quantization

가중치(필요하면 활성값과 KV까지)를 더 적은 비트로 표현해 메모리와 대역폭을 줄이는 기법입니다. 선택 기준은 GPU 세대, 품질 허용치, 서빙 엔진 지원 여부 세 가지입니다.

쉽게 말하면 · 양자화는 사진 압축이다

고화질 사진을 JPG로 압축하면 용량이 확 줄고, 눈으로 보면 거의 차이가 없습니다. 양자화도 같습니다. 숫자 하나를 16비트 대신 8비트나 4비트로 저장해서, 70B 모델이 140GB에서 70GB, 약 38.5GB로 줄어듭니다.

다만 압축한 사진이 원본과 똑같은 사진은 아니듯, 많이 줄일수록 세부가 조금씩 뭉개집니다. 그래서 어떤 형식을 쓸 수 있는지는 GPU 세대가 정하고, 얼마나 줄여도 되는지는 실제 업무 질문으로 확인해서 정합니다.

양자화가 실제로 하는 일

4비트 정수는 -8부터 7까지 16개 값만 표현할 수 있습니다. 그래서 가중치를 128개 정도씩 묶고, 묶음마다 "정수 1칸이 실제로 얼마인지"를 나타내는 스케일 값을 하나씩 따로 저장합니다. 쓸 때는 정수에 스케일을 곱해 원래 값에 가깝게 되돌립니다.

실제 가중치 ≈ 4비트 정수 × 묶음의 스케일예: 스케일이 0.02인 묶음에서 정수 -3은 -0.06을 뜻합니다. 스케일도 메모리를 차지해서 INT4는 파라미터당 0.5가 아니라 약 0.55바이트가 됩니다.

AWQ, GPTQ 같은 W4A16 방식은 이렇게 저장만 4비트로 하고, 계산 직전에 16비트로 풀어서 원래대로 계산합니다. 그러니 계산량은 그대로인데 왜 빨라질까요? 2편에서 보겠지만 답을 한 글자씩 만드는 decode 단계는 계산이 아니라 GPU 메모리에서 가중치를 읽어 오는 속도에 묶여 있어서, 읽을 바이트가 1/4로 줄면 그만큼 빨라집니다. 반대로 FP8 W8A8은 계산 자체도 8비트로 해서, FP8 전용 연산 장치가 있는 Hopper·Ada에서 계산까지 빨라집니다.

방식비트무엇을 줄이나품질맞는 GPU
BF16 / FP1616기준원본전부
FP8 (W8A8)8가중치·활성값, 연산도 FP8거의 무손실Ada(L40S, 4090), Hopper(H100/H200), Blackwell

고르는 순서

  1. BF16으로 들어가고 KV가 넉넉하면 양자화하지 않습니다. 품질 검증 비용이 0입니다.
  2. Hopper·Ada면 FP8부터. 메모리 절반, 연산도 빨라지고 품질 손실이 거의 없습니다.
  3. Ampere면 INT8 W8A8 또는 AWQ INT4. A100은 FP8 텐서코어가 없어 FP8 체크포인트를 올려도 메모리만 줄고 연산 이득은 없습니다.
  4. 그래도 안 들어가면 INT4. 반드시 실제 업무 질문 세트로 BF16 대비 비교 평가를 합니다.
  5. 동시 요청이 문제면 FP8 KV cache. 같은 메모리로 KV 토큰 수가 두 배가 됩니다.
자주 하는 실수

양자화는 "더 작은 모델"이 아니라 "같은 모델의 근사"입니다. 70B INT4가 32B BF16보다 대체로 낫지만, 긴 문맥 추론이나 숫자 계산은 업무 데이터로 직접 확인해야 합니다.

VRAM 계산기

조건을 바꾸며 어디서 OOM이 나는지, 동시 몇 명까지 받을 수 있는지 확인해 보세요. 예시 값은 70B를 A100 80GB 한 장에 BF16으로 올리는 경우이고, 아래 순서로 바꿔 보면 위 메모리와 양자화 내용이 숫자로 확인됩니다.

  1. 기본값(70B, BF16, A100 1장) 그대로 두고 "로딩 OOM"이 뜨는지 확인
  2. 가중치 정밀도를 INT4로 바꾸기 → 기동은 되지만 동시 요청이 몇 개까지 되는지 보기
  3. GPU를 H100, GPU 수를 2, 정밀도를 FP8로 바꾸기 → 여유가 얼마나 생기는지 보기
  4. 동시 요청 수를 늘려 가며 "대기열 발생"이 뜨는 지점 찾기

근사 계산입니다. 오버헤드는 GPU당 3GB로 가정했고, decode 속도는 "토큰 1개마다 가중치를 한 번 읽는다"는 대역폭 상한에 효율 60%를 곱한 값입니다. 실제 숫자는 vLLM 기동 로그의 GPU KV cache size로 확인하세요.

70B를 A100 80GB 한 장에 올렸더니 OOM

계산: 가중치 BF16 140GB, 사용 가능 메모리 80 × 0.9 = 72GB. 가중치 로딩 도중 CUDA out of memory가 납니다. 설정 문제가 아니라 산수 문제입니다.

H100 80GB에 FP8로 바꿔도 가중치 70GB + 오버헤드 약 3GB로 72GB를 넘거나 거의 꽉 차서 No available memory for the cache blocks가 납니다. 가중치가 "들어간다"와 "서비스가 된다"는 다릅니다.

선택지

  • A100 1장 유지: AWQ INT4(약 38.5GB)로 KV 약 30GB 확보 → 8K 기준 동시 11개, FP8 KV 미지원 환경이면 여기서 끝
  • A100 2장 TP=2: INT8 W8A8(장당 35GB)로 KV 합산 약 68GB → 8K 기준 동시 25개 안팎
  • H100 2장 TP=2: FP8 가중치 + FP8 KV → 8K 기준 동시 50개 이상, 품질 손실 최소

정리하면, 메모리 계산, 양자화, GPU 세대(2편), 동시 요청 수(3편)가 모두 하나의 계산으로 이어집니다. "백과사전이 책상에 올라가는가 → 메모장 자리가 몇 명분 남는가"를 차례로 따지면 어떤 GPU에 어떤 형식으로 올릴지가 정해집니다.

어떤 Quantization을 써야 하나

  • H100·L40S가 있다: FP8. 고민할 이유가 거의 없음
  • A100·A6000만 있다: 메모리가 빠듯하면 AWQ INT4(Marlin 커널), 여유가 있으면 INT8 W8A8
  • RTX 4090 같은 24GB 카드: 70B는 INT4로도 한 장에 안 들어감. 2장 TP라도 KV가 거의 남지 않아 실서비스 불가. 32B INT4나 8B급이 현실적인 범위
  • 공통: 업무 질문 100~200개를 BF16 결과와 나란히 비교한 뒤 결정. 공개 벤치마크 점수 차이가 작아도 특정 도메인에서 무너질 수 있음
