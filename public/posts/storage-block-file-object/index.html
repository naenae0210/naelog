블록, 파일, 오브젝트 스토리지는 무엇이 다른가: 디스크 바닥부터 MinIO까지

셋 다 결국 같은 디스크에 저장합니다. 차이는 데이터를 어떤 단위로 자르고, 어떤 이름으로 부르고, 누가 어떤 길로 꺼내 가느냐에 있습니다. 그 차이를 디스크 바닥부터 한 층씩 올라가며 봅니다.

2026.11.2320분 스토리지파일 시스템S3MinIO

"DB는 왜 EBS에 두고 사진은 왜 S3에 두나요?" 이 질문에 제대로 답하려면 결국 디스크가 데이터를 어떻게 저장하는지, 운영체제가 그 디스크를 어떻게 다루는지까지 내려가야 합니다. 이 글은 물리 매체에서 시작해 운영체제, 블록, 파일, 오브젝트 순서로 한 층씩 쌓아 올립니다. 다 읽고 나면 각 층이 왜 그런 모양인지, 그래서 어떤 일에 맞는지를 스스로 설명할 수 있게 됩니다.

쉽게 말하면 · 창고 세 곳

같은 물건을 맡기는 창고가 세 종류 있다고 생각해 보세요.

  • 블록 스토리지: 번호만 붙은 빈 선반 칸을 통째로 빌려줍니다. 무엇을 어느 칸에 둘지는 빌린 사람이 정리합니다. 창고는 "37번 칸에 뭐가 있는지" 모릅니다.
  • 파일 스토리지: 선반에 폴더와 이름표를 붙여 정리해 주는 사서가 있습니다. "사진 폴더의 cat.jpg 주세요" 하면 찾아 주고, 한 장만 고쳐 끼우는 것도 됩니다.
  • 오브젝트 스토리지: 택배 보관소입니다. 상자를 통째로 맡기고 송장 번호(키)를 받고, 찾을 때도 번호로 상자를 통째로 받습니다. 대신 보관소를 아무리 키워도 운영이 쉽고, 어디서나 인터넷으로 맡기고 찾을 수 있습니다.

같은 사진 한 장을 세 방식으로 저장하면

먼저 결과부터 보겠습니다. 똑같은 cat.jpg(약 2.4MB)를 세 방식에 저장했을 때 각자 이 사진을 어떻게 "알고" 있는지입니다.

# 블록: "사진"이라는 개념이 없습니다
LBA 1048576 ~ 1049181  (606블록 × 4KiB)  ← 이 범위에 바이트가 써져 있을 뿐
# 이게 사진인지, 어디서 시작하는지는 위에 올린 파일 시스템만 압니다

# 파일: 경로와 장부가 있습니다
/data/photos/2026/cat.jpg
inode 1310722 · size 2481152 · owner kim · mode 0644
→ 데이터 블록: 1048576-1049181

# 오브젝트: 버킷과 키, 그리고 HTTP 주소가 있습니다
버킷: photos   키: 2026/cat.jpg
ETag: "9b2cf535f27731c974343645a3985328" · Content-Type: image/jpeg
GET https://s3.example.com/photos/2026/cat.jpg   # 인증만 되면 어디서든

블록은 숫자만 알고, 파일은 이름과 장부를 알고, 오브젝트는 이름과 장부에 더해 "어디서든 꺼내 가는 주소"까지 압니다. 그리고 파일의 데이터 블록 번호(1048576-1049181)가 블록 쪽 번호와 같다는 점에 주목해 주세요. 파일은 블록 위에 얹혀 있고, 오브젝트 스토리지도 결국 어딘가의 파일과 블록 위에 얹혀 있습니다. 왜 이렇게 쌓이는지, 맨 아래 디스크부터 올라가 보겠습니다.

맨 아래: 디스크는 정해진 크기로만 읽고 씁니다

물리 매체는 파일도 오브젝트도 모릅니다. 정해진 크기 단위로 데이터를 읽고 쓸 뿐입니다. 그런데 그 단위와 속도가 매체마다 달라서, 위층의 설계가 여기에 맞춰집니다.

HDD: 원판이 돌아오기를 기다립니다

HDD는 자성을 입힌 원판(플래터)이 빠르게 돌고, 그 위를 헤드가 오가며 자기장을 바꿔 0과 1을 기록합니다. 원판 표면은 동심원 모양의 트랙으로, 트랙은 다시 섹터라는 조각으로 나뉩니다. 섹터 하나가 읽고 쓰는 최소 단위이고, 전통적으로 512바이트, 요즘은 4KiB를 많이 씁니다.

HDD가 느린 이유는 이 기계적인 움직임에 있습니다. 읽으려면 먼저 헤드를 원하는 트랙으로 옮기고(탐색, seek), 원하는 섹터가 헤드 아래로 돌아올 때까지 기다려야 합니다(회전 지연, rotational latency). 7,200rpm 디스크는 한 바퀴에 약 8.3ms가 걸리니, 평균적으로 반 바퀴인 약 4.2ms를 기다립니다. 여기에 탐색 시간 수 ms가 더해지면 무작위 위치를 한 번 읽는 데 10ms 가까이 걸리고, 초당 처리할 수 있는 무작위 읽기는 100~200번 정도에 그칩니다. 반면 이미 헤드가 있는 자리에서 이어서 읽는 순차 읽기는 원판이 도는 대로 쭉 읽으면 되니 훨씬 빠릅니다.

이 차이가 위층 설계를 오랫동안 지배했습니다. 파일 시스템이 파일을 되도록 연속된 블록에 두려고 하고, DB가 변경 내용을 로그 파일 끝에 이어 쓰는(append) 방식을 좋아하는 이유가 여기서 나옵니다. 무작위 쓰기를 순차 쓰기로 바꾸면 헤드가 덜 움직이기 때문입니다.

SSD: 덮어쓰지 못하는 메모리

SSD는 NAND 플래시 칩의 셀에 전하를 가두어 저장합니다. 움직이는 부품이 없으니 탐색도 회전 지연도 없고, 어느 위치든 거의 같은 속도로 읽습니다. 그런데 NAND에는 HDD에 없던 까다로운 규칙이 있습니다.

  • 읽고 쓰는 단위는 페이지(보통 4~16KiB)입니다.
  • 지우는 단위는 페이지 수백 개를 묶은 블록입니다.
  • 이미 데이터가 있는 페이지에는 바로 덮어쓸 수 없습니다. 블록 전체를 지운 다음에야 다시 쓸 수 있습니다.

그래서 SSD 안에는 FTL(Flash Translation Layer)이라는 컨트롤러 소프트웨어가 있습니다. 바깥에서 "논리 주소 100번을 덮어써 줘"라는 요청이 오면, FTL은 제자리에 덮어쓰지 않고 비어 있는 새 페이지에 쓴 뒤, 주소표를 "100번은 이제 저 페이지"로 고칩니다. 옛 페이지는 무효 표시만 해 둡니다.

무효 페이지가 쌓이면 FTL은 백그라운드에서 가비지 컬렉션(GC)을 합니다. 아직 유효한 페이지를 다른 블록으로 옮겨 적고, 그 블록을 통째로 지워 빈 공간을 되찾습니다. 이때 사용자가 쓴 것보다 디스크가 실제로 더 많이 쓰게 되는 현상을 쓰기 증폭(write amplification)이라고 합니다. NAND 셀은 지우고 쓸 수 있는 횟수에 수명이 있어서, 쓰기 증폭이 크면 SSD가 빨리 닳습니다.

운영체제가 파일을 지워도 SSD는 그 사실을 모릅니다. 바깥에서 본 SSD는 "주소 몇 번에 데이터가 있다"만 알지 "그 데이터가 이제 필요 없다"는 모르기 때문입니다. 그래서 운영체제가 TRIM 명령으로 "이 주소들은 이제 비었다"고 알려 주면, FTL이 GC 때 그 페이지를 옮기지 않아도 되어 성능과 수명이 좋아집니다.

"블록"이라는 말이 두 번 나옵니다

NAND의 "블록"(지우는 단위, 보통 수 MiB)과 뒤에서 볼 "블록 스토리지"의 블록(운영체제가 보는 읽기·쓰기 단위, 보통 4KiB)은 전혀 다른 층의 말입니다. FTL이 둘 사이를 번역해 주기 때문에, 바깥에서는 NAND 내부 사정을 몰라도 됩니다.

NVMe: 매체가 아니라 연결 방식입니다

같은 NAND 칩을 써도 SATA SSD와 NVMe SSD는 속도가 크게 다릅니다. 차이는 매체가 아니라 컴퓨터와 이어지는 방식에 있습니다. SATA는 원래 HDD를 위해 만든 규격이라, 명령을 담는 줄(큐)이 하나뿐이고 그 줄에 32개까지만 세울 수 있습니다. HDD는 어차피 헤드가 하나라 이걸로 충분했지만, 동시에 여러 곳을 읽을 수 있는 SSD에게는 병목입니다. NVMe는 PCIe 버스에 바로 붙고, 큐를 최대 6만 5천여 개, 큐마다 명령을 6만 5천여 개까지 둘 수 있습니다. 보통 CPU 코어마다 자기 큐를 하나씩 가져서, 코어들이 서로 기다리지 않고 동시에 명령을 넣습니다.

대략적인 감을 잡기 위해 매체별 지연을 나란히 보면 이렇습니다. 제품과 조건에 따라 크게 달라지는 일반적인 값이라, 자릿수 차이만 보면 됩니다.

매체무작위 4KiB 읽기 한 번왜 그 정도인가
HDD (7,200rpm)수~10ms헤드 이동과 회전 대기
SATA SSD약 100μs기계 움직임은 없지만 큐 하나와 옛 규격의 오버헤드
NVMe SSD수십~100μsPCIe 직결, 코어별 큐
DRAM (비교용)약 100ns전기 신호만으로 읽음

결국 모두 LBA로 보입니다

HDD의 섹터든 SSD의 페이지든, 컨트롤러를 거치고 나면 바깥에는 똑같은 모습으로 보입니다. 0번부터 시작하는 고정 크기 칸의 긴 배열이고, 할 수 있는 말은 "LBA(Logical Block Address) N번부터 M개 읽어 줘, 써 줘" 두 가지뿐입니다. HDD의 헤드 위치도, SSD의 FTL 주소표도 이 뒤에 숨습니다. 물리 매체에서 위로 올라가는 첫 관문은 예외 없이 이 블록 단위이고, 지금부터 볼 모든 층이 이 LBA 위에 얹힙니다.

운영체제가 디스크를 다루는 길

프로그램이 파일을 읽을 때 디스크에 바로 손을 대는 게 아닙니다. 그 사이에 운영체제가 여러 층을 두고 일을 나눠 맡습니다. 리눅스에서 read() 한 번이 지나가는 길을 따라가 보면, 뒤에서 볼 블록과 파일 스토리지의 경계가 어디인지 분명해집니다.

  1. 시스템 콜: 프로그램이 read()를 부르면 실행이 사용자 공간에서 커널로 넘어갑니다. 프로그램은 디스크를 직접 만지지 못하고, 항상 커널에 부탁합니다.
  2. VFS(Virtual File System): 리눅스는 ext4, XFS, NFS 등 어떤 파일 시스템이든 같은 입구로 받습니다. 그래서 프로그램은 밑에 무엇이 있든 똑같이 open, read를 부를 수 있습니다.
  3. 파일 시스템: "이 파일의 0~4,095바이트"를 "LBA 1,048,576번 블록"으로 번역합니다. 이 번역에 쓰는 장부가 뒤에서 볼 inode입니다.
  4. 페이지 캐시: 커널은 최근에 읽거나 쓴 디스크 내용을 남는 메모리에 담아 둡니다. 원하는 블록이 이미 메모리에 있으면 디스크까지 가지 않고 여기서 바로 돌려줍니다. 같은 파일을 두 번째 읽을 때 훨씬 빠른 이유입니다.
  5. 블록 계층: 캐시에 없으면 LBA 단위의 읽기 요청을 만듭니다. 근처 요청을 하나로 합치고, 장치에 맞게 순서를 정한 뒤(I/O 스케줄러) 드라이버에 넘깁니다.
  6. 드라이버와 장치: NVMe 드라이버가 요청을 장치의 큐에 넣고, 장치가 데이터를 메모리로 보내면 거꾸로 올라가 프로그램의 buf에 담깁니다.

쓰기는 일단 메모리에, fsync가 있어야 디스크에

쓰기에서는 페이지 캐시가 더 중요한 역할을 합니다. write()는 보통 데이터를 페이지 캐시에 적고 "더러운(dirty)" 표시만 한 뒤 바로 돌아옵니다. 실제로 디스크에 내려가는 건 커널이 나중에 몰아서 처리할 때입니다. 덕분에 쓰기가 빠르지만, 그 사이에 전원이 나가면 write()가 성공했는데도 데이터가 사라질 수 있습니다.

그래서 fsync()가 있습니다. "이 파일의 변경 내용을 디스크에 확실히 내려 줄 때까지 기다리겠다"는 뜻입니다. DB가 트랜잭션을 커밋할 때마다 로그 파일에 쓰고 fsync()를 부르는 것도, 성공했다고 답한 데이터는 정전이 나도 남아 있어야 하기 때문입니다. 이 한 번의 fsync()가 디스크 지연을 그대로 겪는 순간이라, DB의 커밋 속도는 결국 그 밑에 깔린 블록 장치의 쓰기 지연에 묶입니다.

페이지 캐시를 일부러 건너뛰는 방법도 있습니다. 파일을 O_DIRECT로 열면 커널 캐시를 거치지 않고 장치와 바로 주고받습니다. 자기만의 캐시를 따로 관리하는 DB가 운영체제 캐시와 같은 데이터를 두 번 들고 있지 않으려고 이 방식을 쓰기도 합니다.

블록 스토리지: LBA를 그대로 빌려줍니다

블록 스토리지는 앞에서 본 LBA 배열을 거의 그대로 서버에 빌려주는 방식입니다. 이름도, 폴더도, 권한도 없고, 할 줄 아는 말은 이것뿐입니다.

# 블록 장치가 이해하는 명령은 사실상 이것뿐
READ  (LBA=1048576, 개수=8)   # 1048576번 블록부터 8개 = 32KiB 읽기
WRITE (LBA=1048576, 개수=8, 데이터)

서버에 꽂힌 SSD, 클라우드에서 붙인 EBS 볼륨, 스토리지 장비가 네트워크로 넘겨주는 볼륨(LUN)이 모두 서버 입장에서는 /dev/nvme1n1 같은 빈 블록 장치로 보입니다. 그 상태로는 파일을 넣을 수 없고, 서버의 OS가 그 위에 파일 시스템을 만들어야(포맷) 폴더와 파일이 생깁니다. 위 그림으로 말하면 블록 스토리지는 "블록 계층 아래"만 빌려주고, 그 위 파일 시스템과 페이지 캐시는 빌린 서버가 직접 맡습니다.

# 1) 붙어 있는 블록 장치 보기
$ lsblk
NAME        SIZE TYPE MOUNTPOINT
nvme0n1      50G disk
└─nvme0n1p1  50G part /
nvme1n1     500G disk              # 새로 붙인 볼륨. 아직 이름도 폴더도 없음

# 2) 그 위에 파일 시스템 만들기 (블록 → 파일 층으로)
$ sudo mkfs.xfs /dev/nvme1n1
$ sudo mount /dev/nvme1n1 /data
$ df -h /data                      # 이제 /data 아래에 파일을 쓸 수 있음

네트워크 블록 (SAN)iSCSI, Fibre Channel, NVMe-oFLBA 명령을 네트워크로 보냄. 서버에는 로컬 디스크처럼 보임
클라우드 볼륨AWS EBS, GCP Persistent Disk, Azure Managed Disk네트워크 블록을 서비스로 판매. 스냅샷, 크기 변경 가능
분산 블록Ceph RBD, Longhorn여러 서버 디스크를 묶어 하나의 볼륨처럼. 쿠버네티스 PV로 많이 씀

블록 스토리지는 아무것도 모르기 때문에 빠릅니다. 경로를 해석하거나 권한을 확인하는 층이 없어서 "정확히 이 위치의 4KiB만 바꿔 줘" 같은 작고 잦은 요청을 가장 짧은 경로로 처리합니다. DB는 자기 데이터 파일 안에서 8KiB 같은 페이지 단위로 쉴 새 없이 제자리 덮어쓰기를 하고, 커밋마다 fsync()를 기다립니다. 그래서 DB와 가상머신 디스크가 블록 스토리지에 놓입니다. 이때 보는 지표는 초당 처리 횟수(IOPS)와 한 번의 지연입니다.

한 볼륨은 한 서버가 씁니다

파일 시스템의 장부와 페이지 캐시는 그 볼륨을 마운트한 서버의 메모리에 있습니다. 두 서버가 같은 블록 장치에 각자 ext4를 올려 동시에 쓰면, 서로의 캐시와 장부 변경을 모른 채 덮어써서 파일 시스템이 깨집니다. 공유하려면 클러스터 파일 시스템이나 EBS Multi-Attach 같은 특수 기능이 필요합니다.

파일 스토리지: 번호 위에 이름의 장부를 얹습니다

파일 시스템(ext4, XFS, NTFS, APFS 등)은 블록 장치 일부를 장부로 쓰면서, 나머지 블록에 담긴 데이터가 누구의 것인지 기록합니다. 장부의 핵심은 세 가지입니다.

구성 요소하는 일
inode파일 하나의 정보 카드. 크기, 소유자, 권한, 수정 시간, 데이터가 있는 블록 번호 목록. 파일 이름은 여기에 없음
디렉터리"이름 → inode 번호" 표를 담은 특별한 파일. photos/는 그 안의 이름표 목록일 뿐
저널정전이 나도 장부가 깨지지 않도록 장부 변경을 먼저 적어 두는 기록장

이름이 inode가 아니라 디렉터리에 있다는 점이 중요합니다. 그래서 /data/photos/2026/cat.jpg를 열면 파일 시스템은 경로를 한 칸씩 따라 내려갑니다.

이 구조 덕분에 파일 시스템은 사람이 쓰기 편한 기능을 줍니다. 경로로 찾고, 파일 중간의 몇 바이트만 고치고, 폴더 이름을 장부 한 줄만 고쳐 순식간에 바꿉니다. 프로그램은 open, read, write, lseek, close 같은 시스템 콜로 이 기능을 쓰는데, 이 규칙 모음이 POSIX이고 대부분의 프로그램이 이걸 전제로 만들어져 있습니다.

# 파일의 inode 정보 보기
$ stat /data/photos/2026/cat.jpg
  Size: 2481152    Blocks: 4848   IO Block: 4096   regular file
 Inode: 1310722    Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/  kim)

# 파일 중간 몇 바이트만 고치기: 파일 시스템이라서 가능
$ printf 'XY' | dd of=cat.jpg bs=1 seek=100 conv=notrunc

여러 서버가 같은 폴더를 보려면: NAS

로컬 파일 시스템은 한 서버의 메모리에 장부와 캐시가 있어서 그 서버만 씁니다. 여러 서버가 같은 폴더를 보려면 파일 시스템을 한 곳(파일 서버, NAS)에 두고, 그 파일 시스템을 NFS나 SMB 같은 네트워크 프로토콜로 공유합니다. 클라이언트는 블록이나 장부를 직접 다루지 않고 네트워크 너머로 "이 파일 읽어 줘, 이 폴더 목록 줘"라고 요청합니다. 잠금과 권한, 캐시 일관성을 이 프로토콜 계층에서 조정하기 때문에 여러 서버가 동시에 써도 안전하지만, 그 조정과 왕복만큼 지연이 늘어납니다.

위 경로 찾기 그림을 떠올려 보면, 작은 파일 수백만 개를 다루는 작업이 NFS에서 유난히 느린 이유가 보입니다. 파일마다 이름 찾기와 속성 확인이 네트워크 왕복으로 일어나기 때문입니다. 같은 이유로 하나의 파일 시스템을 수십억 개 파일, 여러 지역으로 키우는 것은 어렵고 비쌉니다. 모든 서버가 하나의 장부와 잠금 상태를 실시간으로 맞춰야 하니까요.

종류예시특징
로컬ext4, XFS, NTFS, APFS한 서버에 붙은 블록 장치 위에 만듦
네트워크 공유NFS, SMB, AWS EFS파일 서버 하나를 여러 서버가 같은 폴더처럼 마운트
분산 / 병렬CephFS, Lustre, GPFS, JuiceFS여러 서버에 데이터를 나누되 POSIX 폴더처럼 보이게 함. HPC, AI 학습 클러스터에서 사용

오브젝트 스토리지: 폴더를 포기하고 확장성을 얻습니다

파일 시스템을 크게 키우기 어려운 이유는 결국 장부였습니다. 트리 모양의 디렉터리, 부분 수정, 잠금을 모두 지키면서 수천 대 서버로 늘리기는 어렵습니다. 오브젝트 스토리지는 그 셋을 과감히 포기합니다.

  • 트리 대신 평평한 이름: 데이터를 버킷이라는 큰 통 안에 "키 → 오브젝트"로 저장합니다. 키는 그냥 문자열입니다.
  • 부분 수정 대신 통째로: 오브젝트는 통째로 쓰고 통째로 읽습니다. 범위 읽기는 되지만, 일부만 고치려면 새 오브젝트로 덮어씁니다.
  • 잠금과 시스템 콜 대신 HTTP: PUT, GET, DELETE 같은 HTTP 요청으로 씁니다. 운영체제의 파일 시스템 층을 거치지 않습니다.

키 2026/cat.jpg의 /는 폴더 구분자가 아니라 문자열의 한 글자입니다. 콘솔에서 폴더처럼 보이는 건 목록을 조회할 때 prefix=2026/, delimiter=/로 잘라서 보여 주는 것입니다. 그래서 "폴더 이름 바꾸기"가 없고, 2026/을 2025/로 바꾸려면 그 아래 오브젝트를 전부 복사하고 지워야 합니다. 파일 시스템에서는 장부 한 줄이면 끝나던 일입니다.

대신 트리를 관리할 필요가 없으니, 키를 해시해서 수많은 서버에 나눠 담기가 아주 쉬워집니다. 어느 서버에 있는지는 키만 보고 계산하면 되고, 모두가 함께 맞춰야 하는 하나의 장부가 없습니다. 이것이 오브젝트 스토리지가 수 PB, 수십억 개까지 늘어나면서도 GB당 가장 싼 비결입니다.

# CLI로 올리고 받기 (엔드포인트만 바꾸면 AWS S3든 MinIO든 같은 명령)
$ aws s3 cp cat.jpg s3://photos/2026/cat.jpg --endpoint-url http://localhost:9000

# 실제로 오가는 건 평범한 HTTP 요청
PUT /photos/2026/cat.jpg HTTP/1.1
Host: localhost:9000
Content-Type: image/jpeg
x-amz-meta-owner: kim                 # 사용자 정의 메타데이터
Authorization: AWS4-HMAC-SHA256 ...   # 서명으로 인증

# 파이썬 (boto3): 로그인 없이 10분 동안만 쓸 수 있는 다운로드 링크
import boto3
s3 = boto3.client("s3", endpoint_url="http://localhost:9000")
url = s3.generate_presigned_url("get_object",
      Params={"Bucket": "photos", "Key": "2026/cat.jpg"}, ExpiresIn=600)

대가도 분명합니다. 요청마다 HTTP 왕복과 분산 소프트웨어를 거치니 한 번의 지연은 수~수십 ms로 셋 중 가장 깁니다. 그래서 오브젝트 스토리지는 "한 번 쓰고 여러 번 읽고, 양이 많고, 여기저기서 꺼내 가는" 데이터에 맞습니다. 이런 데이터를 위해 버전 관리(덮어써도 옛 버전 보관), 수명 주기 규칙(오래된 것을 싼 등급으로 자동 이동), Object Lock(정해진 기간 동안 삭제 불가), 멀티파트 업로드(큰 파일을 조각으로 나눠 병렬 업로드) 같은 기능이 붙어 있습니다.

MinIO가 디스크 위에서 실제로 하는 일

오브젝트 스토리지도 결국 디스크에 저장합니다. 그렇다면 "디스크에 파일 넣기"와 무엇이 다를까요? MinIO 내부를 따라가 보면 분명해집니다. 서버 4대에 디스크 4개씩, 총 16개 디스크로 클러스터를 만들었다고 해 보겠습니다.

  1. 어디에 둘지 정하기: 디스크들은 erasure set(예: 16개 한 묶음) 단위로 묶입니다. 키 2026/cat.jpg를 해시해서 어느 묶음에 저장할지 정하니, 중앙 장부를 찾아볼 필요가 없습니다.
  2. 쪼개고 패리티 만들기: 데이터를 12조각으로 나누고, 이 조각들로부터 패리티 4조각을 계산합니다(erasure coding). 패리티는 "잃어버린 조각을 계산으로 되살리기 위한 여분 정보"입니다.
  3. 디스크마다 기록: 각 디스크의 XFS 위에 /mnt/disk1/photos/2026/cat.jpg/xl.meta(메타데이터, 버전, 체크섬)와 .../part.1(이 디스크가 맡은 조각)처럼 저장합니다. 이름은 cat.jpg지만 폴더이고, 안에는 조각 하나만 있습니다.
  4. 읽을 때: 조각을 모아 체크섬으로 손상 여부를 확인하고, 필요하면 패리티로 복구해 하나로 이어 돌려줍니다. 손상된 조각은 백그라운드에서 고쳐 씁니다(healing).

즉 오브젝트 스토리지는 파일 시스템을 부품으로 쓰는 분산 시스템입니다. 그래서 MinIO 문서도 디스크를 RAID나 NFS로 묶지 말고, 각 디스크에 XFS를 따로 올려 그대로 넘기라고 권합니다. 복구와 분산은 MinIO가 직접 하기 때문입니다.

참고 · MinIO 커뮤니티 에디션의 현재 (2026년 11월 기준)

MinIO는 Go로 만든 단일 바이너리 하나로 S3 호환 스토리지를 띄울 수 있어 널리 쓰였지만, 2025년에 커뮤니티 에디션의 콘솔 기능 축소와 Docker 이미지 배포 중단을 거쳐 2026년에는 GitHub 저장소가 아카이브되었습니다. 회사는 상용 제품 AIStor에 집중하고 있어, 새 프로덕션 시스템의 기본 선택지로 권하기는 어렵습니다. 대안으로는 Ceph RGW(대규모, 운영 난도 높음), SeaweedFS(작은 파일 대량), Garage(소규모 셀프호스팅), 그리고 클라우드의 S3, GCS, Azure Blob, Cloudflare R2가 있습니다. 모두 같은 S3 API를 쓰니, 코드에서 표준 S3 호출만 쓰도록 해 두면 엔드포인트와 인증 키만 바꿔 갈아탈 수 있습니다. 도입 전에는 각 제품의 최신 상황을 다시 확인하세요.

챙길 것이유
블록IOPS와 지연을 기준으로 등급을 고르고, 스냅샷을 정기적으로 다른 리전에 복제하고, 볼륨 암호화를 기본으로 켬DB의 커밋 속도가 이 장치의 쓰기 지연에 묶이고, 프로비저닝한 용량만큼 비용이 나감
파일용량뿐 아니라 처리량 등급을 검토하고, 네트워크 접근 제어와 POSIX 권한을 함께 관리하고, 스냅샷과 파일 단위 백업을 병행동시 접근이 늘수록 장부와 잠금을 맞추는 비용이 병목이 됨
오브젝트버킷은 기본 비공개로 두고, 권한 방식(IAM, 버킷 정책, ACL)을 하나로 통일하고, 버전 관리와 수명 주기 규칙을 켬인터넷 어디서나 접근되는 구조라 공개 설정 실수가 곧 유출이고, 쌓일수록 저장 등급 설계가 비용을 좌우함

오브젝트 스토리지는 VPC 안이 아니라 밖의 독립 서비스라는 점도 기억해 둘 만합니다. VPC 안의 서버가 접근할 때는 인터넷을 거치는 퍼블릭 엔드포인트와 내부망만 타는 VPC 엔드포인트(PrivateLink) 중에서 고르고, 보안 그룹만으로 통제된다고 착각하지 않아야 합니다.

  • 블록: 사용자, 게시글, 좋아요 수를 담은 PostgreSQL. 작은 행을 쉴 새 없이 고치고 커밋마다 fsync()하니 빠른 블록 볼륨(EBS gp3, 로컬 NVMe)에 둡니다.
  • 오브젝트: 원본 사진과 썸네일. 한 번 올리면 거의 안 바뀌고 전 세계에서 읽습니다. S3에 두고 CDN을 앞에 붙이며, DB에는 키(2026/11/u42/abc.jpg)만 저장합니다. 업로드는 앱 서버가 presigned URL을 발급하고 브라우저가 S3로 직접 올려서, 앱 서버가 큰 파일을 중계하지 않습니다.
  • 파일: 설정 파일과 빌드 결과물은 서버 로컬 디스크의 평범한 파일입니다.

흔한 실수는 사진을 DB의 BLOB 컬럼에 넣거나 앱 서버 로컬 디스크 /uploads에 저장하는 것입니다. 서버를 두 대로 늘리는 순간 "어느 서버에 올렸더라?" 문제가 생깁니다. 로컬 디스크는 블록 스토리지이고, 블록 스토리지는 한 서버의 것이니까요.

GPU 클러스터에서 모델 학습

  • 오브젝트: 원본 데이터셋(수십 TB)과 체크포인트를 싸고 안전한 오브젝트 스토리지에 보관합니다.
  • 블록: 학습 직전에 데이터를 샤드 단위로 각 노드의 로컬 NVMe에 내려받아, GPU가 가장 빠른 층에서 읽게 합니다.
  • 파일: 여러 노드가 같은 코드와 작은 설정을 함께 봐야 할 때는 Lustre, NFS 같은 공유 파일 시스템을 씁니다.

작은 이미지 수백만 장을 오브젝트 하나하나로 읽으면 요청마다 붙는 HTTP 왕복이 병목이 됩니다. 수백 MB 단위로 묶은 샤드(tar, WebDataset, Parquet 등)로 저장해야 오브젝트 스토리지의 높은 처리량을 제대로 씁니다. 한 번의 지연은 길어도 큰 덩어리를 병렬로 받으면 전체 처리량은 매우 높기 때문입니다.

"MinIO를 NFS 위에 올리면 편하지 않을까?"

NAS가 이미 있으니 NFS로 마운트한 폴더 하나를 MinIO에 넘기면 될 것 같지만, 권장하지 않는 구성입니다. MinIO는 디스크별 조각, 체크섬, 복구를 자기 손으로 관리하도록 설계되었는데, NFS가 그 사이에서 캐시와 잠금을 따로 처리하면 일관성이 깨질 수 있습니다. NFS 서버 하나가 죽으면 전부 멈추니 분산의 이점도 사라집니다. 층은 아래에서 위로 쌓을 때 의미가 있고, 오브젝트 스토리지는 각 서버의 로컬 디스크(블록) 위 XFS에 올리는 것이 정석입니다.

자주 하는 오해

오해실제
"write()가 성공했으니 디스크에 저장됐다"보통은 페이지 캐시에만 적힌 상태입니다. 정전에도 남아야 하는 데이터라면 fsync()까지 해야 합니다.
"SSD는 덮어쓰기가 공짜다"NAND는 제자리 덮어쓰기가 안 되어 FTL이 새 페이지에 쓰고 나중에 GC로 정리합니다. 무작위 쓰기가 많을수록 쓰기 증폭이 커지고 수명이 줄어듭니다.
"S3에도 폴더가 있잖아요"콘솔이 키를 /로 잘라 폴더처럼 보여 줄 뿐입니다. 빈 "폴더"는 2026/이라는 크기 0짜리 오브젝트로 흉내 냅니다.
"s3fs로 마운트하면 파일 시스템이 된다"흉내만 냅니다. 파일 일부를 고치면 뒤에서 오브젝트 전체를 다시 올리고, 잠금과 이름 변경은 제한되거나 느립니다. 읽기 위주 용도에만 쓰세요.
"오브젝트 스토리지는 느리다"한 번의 지연은 길지만 병렬로 많이 요청하면 전체 처리량은 매우 높습니다. 큰 파일을 여러 조각으로 동시에 받으면 수십 GB/s도 나옵니다.
"방금 올린 걸 바로 읽으면 옛것이 나온다"예전 S3 이야기입니다. AWS S3는 2020년 12월부터 쓰기 직후 읽기에 강한 일관성을 보장합니다. 호환 제품마다 다를 수 있으니 확인하세요.
"RAID나 erasure coding이 있으니 백업은 필요 없다"디스크 고장만 막아 줍니다. 실수로 지운 것이나 랜섬웨어는 그대로 복제됩니다. 버전 관리, Object Lock, 다른 위치의 백업이 필요합니다.

정리

  • 물리 매체는 정해진 크기로만 읽고 씁니다. HDD는 헤드와 회전 때문에 무작위 접근이 느리고, SSD는 덮어쓰지 못해 FTL이 주소를 바꿔 가며 쓰고, NVMe는 코어별 큐로 병렬성을 살립니다. 그리고 바깥에는 모두 LBA로 보입니다.
  • 운영체제는 시스템 콜, VFS, 파일 시스템, 페이지 캐시, 블록 계층을 거쳐 LBA 명령을 만듭니다. write()는 메모리에, fsync()가 있어야 디스크에 남습니다.
  • LBA를 그대로 빌려주면 블록 스토리지, 그 위에 이름의 장부를 얹어 공유하면 파일 스토리지, 장부 대신 평평한 키와 분산 소프트웨어로 감싸 HTTP로 내보내면 오브젝트 스토리지입니다.
  • 위로 갈수록 지연은 길어지고 공유와 확장은 쉬워집니다. DB와 VM은 블록, 함께 고치는 폴더는 파일, 많이 쌓고 여기저기서 꺼내는 데이터는 오브젝트에 둡니다.
