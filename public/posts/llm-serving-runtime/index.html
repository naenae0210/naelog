CUDA와 GPU 드라이버

모델을 GPU에서 돌리려면 프로그램과 GPU 사이에 여러 층의 소프트웨어가 필요합니다. 이 층들이 무엇이고 어떻게 이어지는지 알면 설치 오류 대부분이 풀립니다.

CUDA란

CUDA(Compute Unified Device Architecture)는 NVIDIA가 만든 "GPU에게 일을 시키는 방법"입니다. 원래 GPU는 게임 화면을 그리는 장치였지만, 안에 단순한 계산을 동시에 처리하는 작은 일꾼이 수천 명 있어서 행렬 곱셈처럼 같은 계산을 엄청나게 반복하는 일, 바로 AI 모델이 하는 일에 아주 잘 맞습니다. 이 일꾼들에게 그림 말고 다른 일을 시키는 방법이 CUDA입니다. NVIDIA GPU에서만 돌아가고, AMD는 ROCm이라는 별도 방식을 씁니다.

CUDA는 프로그램 하나가 아니라 여러 부품을 묶은 꾸러미입니다.

부품예시하는 일
언어CUDA C++GPU에서 돌아갈 함수(커널)를 쓰는 문법
컴파일러nvcc그 코드를 GPU가 읽는 기계어로 바꿈
런타임 APIcudaMalloc, cudaMemcpy, 커널 실행GPU 메모리 잡기, 데이터 복사, 작업 시키기
라이브러리cuBLAS, cuDNN, NCCL자주 쓰는 계산을 NVIDIA가 미리 최적화해 둔 것
개발 도구Nsight어디가 느린지 재는 프로파일러

라이브러리 중 cuBLAS는 행렬 곱셈을 맡고 LLM 계산의 대부분이 여기서 돕니다. cuDNN은 딥러닝 연산 모음이고, NCCL("니클")은 GPU끼리 데이터를 주고받는 통신 라이브러리라서 GPU 2장으로 tensor parallel을 하면 매 레이어마다 호출됩니다.

PyTorch와 vLLM이 CUDA를 대신 써 준다

CUDA로 배열 두 개를 직접 더하면 이런 모양입니다.

// GPU에서 돌아갈 함수(커널). 일꾼 한 명이 숫자 하나씩 맡음
    __global__ void add(float* a, float* b, float* c, int n) {
        int i = blockIdx.x * blockDim.x + threadIdx.x;  // 나는 몇 번 일꾼인가
        if (i < n) c[i] = a[i] + b[i];
    }

    int main() {
        cudaMalloc(&a, n * 4);  cudaMalloc(&b, n * 4);  cudaMalloc(&c, n * 4);  // GPU 메모리 잡기
        cudaMemcpy(a, host_a, n * 4, cudaMemcpyHostToDevice);  // CPU → GPU 복사
        cudaMemcpy(b, host_b, n * 4, cudaMemcpyHostToDevice);

        add<<<n / 256, 256>>>(a, b, c, n);   // 일꾼 256명짜리 팀을 여러 개 띄워 실행

        cudaMemcpy(host_c, c, n * 4, cudaMemcpyDeviceToHost);  // 결과를 GPU → CPU로
        cudaFree(a); cudaFree(b); cudaFree(c);   // 메모리 반납
    }

덧셈 한 번에도 메모리 잡기, 복사, 일꾼 나누기, 결과 가져오기, 반납까지 직접 챙겨야 합니다. 같은 일을 PyTorch로 하면 한 줄입니다.

import torch
    a = torch.randn(n, device="cuda")   # GPU에 배열 만들기
    b = torch.randn(n, device="cuda")
    c = a + b                           # 끝

a + b 뒤에서 PyTorch가 위 CUDA 코드에 해당하는 일을 알아서 합니다. 메모리를 잡고, 미리 만들어 둔 덧셈 커널을 고르고, 일꾼 수를 정해 실행합니다. 행렬 곱셈 a @ b라면 내부에서 cuBLAS를 부릅니다. vLLM은 한 단계 더 위라서, PyTorch 코드조차 쓰지 않고 vllm serve 모델이름 한 줄이면 모델 구조를 PyTorch로 짜 두고 요청이 오면 알아서 돌립니다.

밑으로 갈수록 세밀하게 조정할 수 있지만 할 일이 많고, 위로 갈수록 편하지만 세부는 맡기게 됩니다.

요청 하나가 GPU까지 내려가는 흐름

사용자가 "안녕?"을 보내면 지시는 다섯 층을 거쳐 내려가고, 결과는 다시 위로 올라옵니다.

사용자 → ① vLLM → ② PyTorch → ③ CUDA 런타임·라이브러리 → ④ GPU 드라이버 → ⑤ GPU
단계목적하는 일
① vLLM여러 손님을 효율적으로 받기HTTP 요청 수신 → "안녕?"을 토큰 번호로 변환(예: [52, 1031, 30]) → 스케줄러가 다른 요청과 한 배치로 묶음 → KV cache 블록 배정 → PyTorch에 "이 배치로 모델 한 번 돌려 줘" 요청. 대기열·KV 사용률·선점 같은 운영 지표가 전부 여기서 나옴
② PyTorch모델 수식을 GPU 작업 목록으로 번역"80개 층, 층마다 attention과 feed-forward"로 정의된 모델 코드를 따라가며 행렬 곱, softmax, 정규화 같은 연산을 하나하나 GPU 작업으로 바꿈. 텐서가 어느 GPU 메모리에 있는지 관리
③ CUDA 런타임·라이브러리이 계산을 이 GPU에서 가장 빠르게"4096×8192 행렬 곱"이 오면 cuBLAS가 이 GPU 세대와 크기에 가장 빠른 방법을 고름(A100과 H100의 선택이 다름). 커널 실행 명령을 대기 줄(stream)에 순서대로 넣음. GPU 메모리 할당·해제
④ GPU 드라이버운영체제와 하드웨어 사이 통역CUDA 명령을 하드웨어가 알아듣는 신호로 바꿔 GPU 명령 큐에 넣음. 필요하면 커널을 이 GPU용 기계어로 마지막 변환. 여러 프로그램이 한 GPU를 쓰면 순서를 조율하고 메모리가 섞이지 않게 지킴. 프린터를 쓰려면 프린터 드라이버가 필요한 것과 같음
⑤ GPU실제 계산SM 안의 수천 개 코어가 커널을 나눠 동시에 실행. HBM에서 가중치와 KV를 읽고 결과를 씀. 80개 층을 다 지나면 "다음 토큰 후보별 점수"가 나옴
⑥ 다시 위로한 글자를 사용자에게점수에서 다음 토큰 하나를 고르고(샘플링) vLLM이 글자로 바꿔 스트리밍으로 보냄. 그리고 ②~⑤를 토큰 하나마다 반복. 이것이 아래에서 볼 decode

실제로는 ①에서 ③으로 바로 가는 길도 섞여 있습니다. vLLM은 속도가 중요한 부분에서 PyTorch 기본 연산을 건너뛰고 PagedAttention, FlashAttention, 4비트 모델용 Marlin 같은 자체 CUDA 커널을 직접 부르기 때문입니다.

이 흐름에서 숫자 감각도 하나 얻을 수 있습니다. 70B 모델은 토큰 하나를 만드는 동안 80개 층을 지나고 층마다 커널이 여러 개 돌기 때문에, 토큰 하나에 GPU 작업이 수백~수천 번 내려갑니다. CPU가 이 명령을 하나씩 내리는 시간만으로도 느려질 수 있어서, vLLM은 명령 순서를 한 번 녹화해 두고 통째로 다시 틉니다. 1편의 오버헤드 항목과 이 글 로딩 순서의 마지막 단계에 나오는 CUDA graph가 이것입니다.

GPU 안은 어떻게 생겼나

앞에서 GPU를 "일꾼 수천 명이 있는 공장"이라고 했습니다. 추론이 왜 그런 속도로 도는지 이해하려면 이 공장 안에서 계산하는 곳과 재료를 보관하는 곳이 어떻게 생겼는지 알아야 합니다. H100 SXM을 예로 보겠습니다.

  • SM(Streaming Multiprocessor): GPU 안의 계산 블록입니다. H100에는 132개가 있고, 각 SM 안에 행렬 곱 전용 장치인 텐서 코어와 일반 계산용 CUDA 코어, 그리고 아주 빠르지만 작은 레지스터와 공유 메모리(SRAM)가 있습니다.
  • L2 캐시: 모든 SM이 같이 쓰는 중간 저장소입니다. 50MB라 70B 모델의 가중치(140GB)에 비하면 아주 작습니다.
  • HBM: 1편에서 계산한 가중치와 KV cache가 실제로 사는 곳입니다. 크지만 SM 안의 메모리보다 훨씬 멉니다.

오른쪽 숫자가 핵심입니다. H100은 1초에 약 990조 번 곱하고 더할 수 있지만, HBM에서는 1초에 약 3.35조 바이트밖에 읽어 오지 못합니다. 즉 1바이트를 가져오는 동안 약 300번 계산할 수 있습니다. 읽어 온 바이트로 300번 넘게 계산하지 않는 작업은 계산 장치가 아무리 빨라도 메모리를 기다리며 놀게 됩니다. 다음 절의 prefill과 decode 차이가 정확히 여기서 나옵니다.

FlashAttention도 이 구조로 이해할 수 있습니다. attention을 그냥 계산하면 중간 결과(토큰 수 × 토큰 수 크기의 점수표)를 HBM에 썼다가 다시 읽어야 합니다. FlashAttention은 계산을 작은 조각으로 나눠 SM 안의 SRAM에서 끝까지 처리하고 결과만 HBM에 씁니다. 계산량은 같지만 느린 HBM 왕복을 크게 줄여서 빨라지고, 긴 컨텍스트에서도 메모리를 덜 씁니다.

모델 로딩과 추론 구조

요청 하나는 "한 번에 읽기(prefill)"와 "한 토큰씩 쓰기(decode)"라는 성격이 완전히 다른 두 단계를 거칩니다.

로딩

  1. 디스크(safetensors)에서 가중치를 읽어 GPU로 복사. 70B BF16이면 140GB를 읽으므로 NVMe·네트워크 스토리지 속도가 기동 시간을 좌우
  2. Tensor parallel이면 각 레이어의 행렬을 GPU 수만큼 쪼개 나눠 올림. GPU끼리는 매 레이어마다 NVLink/PCIe로 결과를 주고받음
  3. 엔진이 더미 요청으로 최대 활성값 메모리를 측정(profiling)
  4. 남은 메모리를 전부 KV cache 블록으로 미리 잡음. 그래서 vLLM 기동 직후 nvidia-smi 사용량이 90%로 보이는 것이 정상
  5. CUDA graph 캡처 후 요청 수신 시작

Prefill과 decode

prefill은 질문지를 한 번에 쭉 읽는 단계이고, decode는 답을 한 글자씩 써 내려가는 단계입니다.

PrefillDecode

늘어나는 조건긴 프롬프트, RAG 문서 대량 첨부긴 답변, 큰 모델, 큰 배치

산술 강도로 보면

"어떤 작업이 계산에 묶이나, 메모리에 묶이나"는 산술 강도(arithmetic intensity), 즉 메모리에서 1바이트를 읽어 몇 번 계산하는지로 판단합니다. 앞 절에서 본 H100의 기준선은 약 300입니다.

  • decode, 요청 1개: 토큰 하나를 만들려면 가중치 전체를 한 번 읽고, 가중치 하나마다 곱하고 더하기를 한 번씩 합니다. BF16 가중치 2바이트를 읽어 계산 2번이니 산술 강도는 약 1입니다. 기준선 300에 한참 못 미쳐서, 계산 장치는 시간의 99% 넘게 메모리를 기다립니다.
  • decode, 요청 64개를 한 배치로: 같은 가중치를 한 번 읽어 64개 요청에 모두 씁니다. 산술 강도가 약 64로 올라가 효율이 그만큼 좋아집니다. 이것이 배칭의 원리입니다.
  • prefill, 프롬프트 2,000토큰: 가중치를 한 번 읽어 2,000개 토큰에 한꺼번에 씁니다. 산술 강도가 기준선을 훌쩍 넘어, 이번에는 계산 장치가 바쁘고 메모리가 남습니다.

이 그림 하나로 세 편이 이어집니다. 1편의 양자화는 읽을 바이트를 줄여 비탈 위의 decode를 빠르게 하고, 배칭은 점을 오른쪽으로 옮기고, 3편의 "동시 요청이 늘면 처리량이 오르다 평평해진다"는 점이 기준선에 닿는 순간입니다. 엄밀히는 attention이 요청마다 자기 KV cache를 따로 읽어야 해서, 배치를 키워도 그 부분의 산술 강도는 오르지 않습니다. 긴 컨텍스트 요청이 많을수록 배칭 효과가 줄어드는 이유입니다.

decode가 메모리 대역폭에 묶이는 이유는 글자 하나를 쓸 때마다 백과사전(가중치) 전체를 한 번 훑어야 하기 때문입니다. 배치 크기 1에서 토큰 하나를 만들려면 가중치 전체를 HBM에서 한 번 읽어야 합니다. 70B BF16(140GB)을 H100 두 장(합산 6.7TB/s)에서 돌리면 이론 상한이 약 48 tok/s입니다. 양자화로 백과사전을 절반으로 얇게 만들면 이 상한도 거의 두 배가 됩니다.

또 한 번 훑은 가중치를 여러 요청이 같이 쓰면 대역폭 비용이 나눠집니다. 버스 한 대에 손님을 여러 명 태우는 것과 같고, 이것이 배칭이 처리량을 올리는 원리입니다.

vLLM

vLLM이 HuggingFace generate()보다 수 배 빠른 이유는 메모리를 아껴 쓰는 기법과 요청을 묶어 처리하는 스케줄링에 있습니다.

  • PagedAttention: KV cache를 운영체제 페이지처럼 작은 블록(기본 16토큰)으로 나눠 필요할 때만 할당. 예전에는 요청마다 최대 길이만큼 메모장을 통째로 미리 잡아서, 대부분 짧게 끝나는 대화 때문에 낭비가 컸습니다. 필요한 만큼만 나눠 주니 같은 메모리에 훨씬 많은 요청이 들어감
  • Continuous batching: 배치가 다 끝나길 기다리지 않고 매 decode 스텝마다 끝난 요청은 빼고 새 요청을 넣음. 정류장마다 내릴 사람은 내리고 탈 사람은 타는 버스와 같음
  • Prefix caching: 같은 시스템 프롬프트·같은 RAG 문서로 시작하는 요청은 그 부분 KV를 한 번만 만들어 같이 씀
  • Chunked prefill: 긴 프롬프트의 prefill을 잘게 나눠 decode 사이에 끼워 넣어, 긴 요청 하나가 다른 사용자의 토큰 생성을 멈추게 하는 일을 줄임

앞의 두 가지는 그림으로 보면 바로 이해됩니다. 먼저 PagedAttention입니다.

다음은 continuous batching입니다. 같은 시간 동안 GPU의 배치 자리 4개가 어떻게 쓰이는지 비교해 보겠습니다.

Tensor parallel은 모델을 어떻게 나누나

70B BF16(140GB)은 GPU 한 장에 들어가지 않으니 여러 장에 나눠 올려야 합니다. tensor parallel은 각 레이어의 큰 행렬을 세로나 가로로 잘라 GPU마다 한 조각씩 들게 합니다. 예를 들어 2장이면 행렬 곱을 반씩 나눠 동시에 계산하고, 각자 만든 부분 결과를 더해 하나로 합칩니다. 이 합치는 통신(all-reduce)을 NCCL이 맡고, 레이어마다 attention 뒤와 feed-forward 뒤 두 번씩 일어납니다. 80개 층이면 토큰 하나에 160번입니다.

그래서 GPU 사이 통로가 중요합니다. H100끼리 잇는 NVLink는 초당 수백 GB를 주고받지만, PCIe로만 연결된 카드는 그보다 열 배 가까이 느려서 통신 시간이 계산 시간을 잡아먹습니다. 같은 "H100 2장"이라도 NVLink 유무에 따라 TP 성능이 크게 달라지는 이유입니다. 모델이 한 장에 들어간다면 굳이 나누지 않는 게 낫고, 이 이야기는 3편의 "TP와 복제본"으로 이어집니다.

설정이 메모리 계산과 어떻게 연결되나

# 70B를 H100 2장에, FP8 가중치 + FP8 KV
    vllm serve meta-llama/Llama-3.1-70B-Instruct \
      --tensor-parallel-size 2 \          # 가중치를 2장에 분할
      --quantization fp8 \                # 140GB → 70GB
      --kv-cache-dtype fp8 \              # KV 토큰 수 2배
      --max-model-len 16384 \             # 요청 하나의 최대 길이
      --gpu-memory-utilization 0.90 \     # 장당 72GB까지 사용
      --max-num-seqs 64                   # 동시에 돌리는 요청 상한

기동 로그에서 반드시 볼 두 줄입니다.

GPU KV cache size: 437,200 tokens
    Maximum concurrency for 16,384 tokens per request: 26.68x

두 번째 줄은 "모든 요청이 16K를 꽉 채우면 동시에 26개까지"라는 뜻입니다. 실제 요청은 대개 더 짧아서 더 많이 들어가지만, 설계는 이 숫자를 기준으로 합니다.

기동 단계 OOM의 대표 메시지

CUDA out of memory. Tried to allocate ...: 가중치 자체가 안 들어감.
No available memory for the cache blocks: 가중치는 들어갔지만 KV 자리가 0.
max seq len (131072) is larger than the maximum number of tokens that can be stored in KV cache: 모델 기본 최대 길이(128K)를 담을 KV가 없음. --max-model-len을 줄이면 해결.
