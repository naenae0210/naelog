LLM 서빙 학습 노트 · 3편
1편메모리와 양자화70B는 왜 A100 한 장에 안 들어갈까 2편GPU 위에서 모델이 돌아가는 방식답은 왜 한 글자씩 나올까 3편 · 지금 읽는 중성능과 운영사용자가 100명이 되면 무엇이 먼저 무너질까

1편: 모델이 들어가려면 가중치 + KV cache + 오버헤드가 GPU 메모리 안에 들어와야 합니다. KV cache 자리가 곧 동시에 받을 수 있는 사람 수입니다.

2편: 답은 한 글자(토큰)씩 만들어지고(decode), 글자 하나마다 가중치 전체를 읽어야 해서 메모리 속도가 병목입니다. 그래서 여러 요청을 한 버스에 태우는 배칭이 효율을 올리고, vLLM이 그 버스를 운영합니다.

이번 편의 질문은 "실제로 사람들이 쓰기 시작하면 어디서 느려지고, 몇 명까지 버티는가?"입니다.

  1. 성능 지표: GPU 사용률의 함정, 응답 시간(TTFT·TPOT·E2E), 처리량
  2. 동시 요청 처리: 사용자가 늘 때 무너지는 순서와 필요한 용량 계산
  3. 사례: 사용자가 10명에서 100명으로 늘면

GPU Utilization, Inference Latency, Throughput

GPU Utilization은 생각보다 많은 걸 숨긴다

nvidia-smi의 GPU-Util 100%는 "샘플링 구간 동안 커널이 하나라도 돌고 있었다"는 뜻일 뿐, SM이 꽉 찼다는 뜻이 아닙니다. 공장 불이 켜져 있다고 일꾼 전원이 일하는 건 아닌 것과 같습니다. decode 위주 부하는 Util 100%이면서 실제 연산 유닛은 20~30%만 쓰는 경우가 흔합니다. 진짜 상태는 DCGM의 SM Activity, DRAM Activity(대역폭 사용률)로 봅니다. 메모리 사용률 90%도 vLLM이 미리 잡아 둔 것이라 부하 지표가 아닙니다. 실제 KV 사용률은 vLLM의 vllm:gpu_cache_usage_perc입니다.

Latency는 세 개로 쪼개서 본다

지표뜻사용자 체감주로 늘리는 원인
TTFT
Time To First Token		요청부터 첫 토큰까지 (대기열 + prefill)"반응이 늦다"긴 프롬프트, 대기열 적체
TPOT / ITL
Time Per Output Token / Inter-Token Latency		토큰과 토큰 사이 간격"글자가 느리게 나온다"큰 배치, 큰 모델, 느린 대역폭
E2E
End-to-End latency		TTFT + TPOT × (출력 토큰 − 1)"답이 다 나오기까지"긴 출력
쉽게 말하면 · 식당으로 비유하면
지표식당 비유
TTFT주문하고 첫 음식이 나오기까지
TPOT / ITL음식과 음식 사이 간격
E2E식사가 전부 나오기까지
p95손님 100명 중 가장 오래 기다린 5명이 기다린 시간

TPOT과 ITL은 거의 같은 뜻으로, 토큰 간격의 평균을 TPOT, 간격 하나하나를 ITL이라고 부릅니다. 세 지표는 이렇게 이어집니다. TTFT 0.5초, TPOT 50ms, 출력 200토큰이면 E2E는 약 0.5 + 0.05 × 199 ≈ 10.5초입니다.

사람이 읽는 속도는 대략 초당 5~10 토큰이므로 스트리밍 채팅이라면 TPOT 100ms 이하, TTFT 1~2초 이하가 흔한 목표입니다. 이때 평균이 아니라 p95, p99(95번째·99번째 백분위수, 즉 느린 쪽 상위 5%·1%)로 봐야 일부 사용자가 겪는 지연이 보입니다. 평균이 괜찮아도 p95가 10초라면 20명 중 1명은 10초 넘게 기다린다는 뜻입니다.

Throughput은 latency와 맞바꾼다

처리량은 "GPU 전체가 초당 생성한 토큰 수"(output tok/s) 또는 "초당 처리 요청 수"(req/s)입니다. 동시 요청이 늘면 가중치 읽기 비용이 여러 요청에 나눠져 전체 처리량은 오르지만, 매 스텝에 처리할 일이 많아져 개별 요청의 TPOT은 늘어납니다. 버스에 손님을 많이 태우면 한 번에 많이 실어 나르지만 정류장마다 타고 내리는 시간이 길어지는 것과 같습니다. 어느 지점부터는 처리량은 거의 그대로인데 지연만 늘어나고, 그 직전이 가장 좋은 운영 지점입니다.

동시 요청요청별 TPOT전체 처리량상태
1가장 짧음매우 낮음GPU 대부분 놀고 있음
8~32조금 늘어남가파르게 증가대역폭을 나눠 쓰며 효율 상승
64+뚜렷하게 늘어남완만해짐연산 또는 KV 한계 접근
KV 한계 초과대기 시간 폭증더 오르지 않음대기열·선점 발생

위 표는 경향을 보여 주는 것이고 정확한 꺾이는 지점은 모델·GPU·입출력 길이마다 다릅니다. vllm bench serve(구버전은 benchmark_serving.py)로 동시성을 바꿔 가며 직접 재야 합니다.

직접 재 보기

위 곡선을 내 환경에서 그려 보는 방법입니다. vLLM에는 부하를 걸어 지표를 재는 벤치마크 도구가 들어 있습니다. 동시 요청 수를 바꿔 가며 여러 번 돌리면 곡선이 나옵니다.

# 서버를 띄운 상태에서, 입력 1,024 / 출력 256 토큰짜리 요청 200개를 동시 32개씩 보냄
    vllm bench serve \
      --model meta-llama/Llama-3.1-70B-Instruct \
      --dataset-name random --random-input-len 1024 --random-output-len 256 \
      --num-prompts 200 --max-concurrency 32

    # --max-concurrency를 1, 8, 16, 32, 64, 128로 바꿔 가며 반복하고
    # 결과의 Output token throughput, Mean/P99 TTFT, Mean/P99 TPOT을 표로 모읍니다

입출력 길이는 실제 서비스와 비슷하게 맞춰야 의미가 있습니다. RAG 서비스라면 입력을 길게, 요약 서비스라면 출력을 길게 잡는 식입니다. 옵션 이름은 vLLM 버전마다 조금씩 다를 수 있으니 vllm bench serve --help로 확인합니다.

운영 중에는 vLLM 서버가 /metrics 주소로 Prometheus 형식의 지표를 내보냅니다.

$ curl -s localhost:8000/metrics | grep -E "num_requests_waiting|cache_usage|preemptions"
    vllm:num_requests_running{...} 41
    vllm:num_requests_waiting{...} 0
    vllm:gpu_cache_usage_perc{...} 0.83
    vllm:num_preemptions_total{...} 12

TTFT와 TPOT은 히스토그램(vllm:time_to_first_token_seconds, vllm:time_per_output_token_seconds)으로 나오므로, Prometheus에서 histogram_quantile(0.95, ...)로 p95를 계산해 대시보드에 올립니다. 지표 이름도 버전에 따라 바뀌기도 해서(예: KV 사용률이 kv_cache_usage_perc로), 쓰는 버전의 /metrics 출력을 한 번 직접 보고 맞추는 게 안전합니다.

동시 요청 처리

사용자가 늘 때 무너지는 순서는 거의 항상 같습니다.

  1. TPOT이 서서히 늘어남: 배치가 커지면서 스텝당 시간이 증가. 아직 정상 범위
  2. KV cache가 차고 대기열이 생김: vllm:num_requests_waiting가 0보다 커짐. 새 요청은 KV 블록이 빌 때까지 기다리므로 TTFT가 급격히 늘어남
  3. 선점(preemption): 진행 중인 요청의 KV가 모자라면 vLLM이 일부 요청을 쫓아냈다가 나중에 처음부터 다시 계산. 같은 일을 두 번 해서 처리량까지 떨어짐. vllm:num_preemptions_total로 확인
  4. 타임아웃: 게이트웨이(nginx, Cloudflare 등)의 대기 한도를 넘어 504. 사용자는 "서버가 죽었다"고 느낌

긴 프롬프트 하나가 다른 사람의 글자를 멈추게 한다

대기열이 없어도 생기는 지연이 있습니다. vLLM은 매 스텝 진행 중인 요청들의 decode와 새로 들어온 요청의 prefill을 한 배치에 함께 처리합니다. 그런데 2만 토큰짜리 RAG 프롬프트가 들어오면 그 prefill이 한 스텝을 길게 붙잡고, 그동안 다른 사용자들은 다음 글자를 받지 못합니다. 사용자 입장에서는 잘 나오던 답변이 갑자기 멈칫하는 것으로 보입니다.

2편의 chunked prefill이 이 문제를 줄입니다. 긴 prefill을 잘게 나눠 여러 스텝에 걸쳐 끼워 넣는 것이고, 한 스텝에 처리할 토큰 수 상한은 --max-num-batched-tokens로 정합니다. 이 값을 작게 하면 다른 사람의 TPOT은 고르게 유지되지만 긴 요청 자신의 TTFT는 늘어나고, 크게 하면 그 반대입니다. 채팅처럼 글자가 끊기지 않는 게 중요하면 작게, 문서 처리처럼 한 번에 끝내는 게 중요하면 크게 잡습니다.

필요한 동시성 계산: Little의 법칙

동시 요청 수 = 초당 요청 수 × 요청당 평균 처리 시간(초)

가게 안 손님 수가 "분당 들어오는 손님 × 한 명이 머무는 시간"인 것과 같은 식입니다. 초당 2건이 들어오고 답변 하나에 평균 15초가 걸리면 늘 30건이 동시에 돌고 있습니다. 이 30건 × 요청당 평균 토큰이 KV 예산 안에 들어와야 대기열 없이 돌아갑니다.

대응 수단

증상먼저 해 볼 것
KV 부족·대기열FP8 KV cache, --max-model-len 축소, 가중치 양자화로 KV 자리 확보, GPU 추가(TP 또는 복제본)
긴 RAG 프롬프트로 TTFT 증가prefix caching, 검색 문서 수·청크 길이 줄이기, chunked prefill
TPOT 증가--max-num-seqs로 배치 상한, 더 작은·양자화 모델, 대역폭 높은 GPU
선점 반복--max-num-seqs 낮추기, KV 확보. 선점은 "조금 덜 받는 게 낫다"는 신호
사용자별 편차게이트웨이에서 사용자당 동시 요청 제한, 출력 토큰 상한(max_tokens)

TP와 복제본은 목적이 다릅니다. TP는 "한 장에 안 들어가는 모델"을 위한 것이고, 들어가는 모델이라면 같은 GPU 수로 복제본을 여러 개 띄우고 로드밸런서로 나누는 쪽이 GPU 간 통신이 없어 처리량이 더 잘 나옵니다.

다만 복제본으로 나누면 KV cache도 서버마다 따로 생긴다는 점을 기억해야 합니다. prefix caching은 같은 서버 안에서만 효과가 있어서, 같은 시스템 프롬프트나 같은 문서를 쓰는 요청이 매번 다른 복제본으로 흩어지면 캐시를 거의 못 씁니다. 대화 세션이나 공통 접두사를 기준으로 같은 복제본에 보내도록 로드밸런서를 설정하면 TTFT를 크게 줄일 수 있습니다.

사례로 다시 보기

사용자가 10명에서 100명으로 늘면

H100 2장, 70B FP8, 요청당 평균 4K 토큰 가정. KV 예산이 40만 토큰 안팎이면 4K 요청은 동시 100개 남짓이 상한입니다.

  1. 10명: 배치가 작아 TPOT 짧음, GPU 대역폭 대부분 낭비
  2. 50명: 처리량이 크게 오르고 TPOT도 함께 늘어남. 체감은 아직 괜찮음
  3. 100명 + 긴 RAG 문서: KV 한계 도달, 대기열 발생, TTFT가 수 초에서 수십 초로 튐
  4. 같은 상태에서 일부가 32K 문서를 넣으면 요청 하나가 4K 요청 8개분 KV를 차지해 선점 발생

그래서 운영에서는 num_requests_waiting, gpu_cache_usage_perc, num_preemptions_total, TTFT p95 네 개를 대시보드에 올려 두고, 대기열이 상시 0이 아니게 되는 시점을 증설 기준으로 잡습니다.

용어 사전 (약자 풀이)

3편에 나오는 약자를 모았습니다. SM, DCGM 같은 GPU 용어는 2편, KV cache 같은 기본 용어는 1편 용어 사전에 있습니다.
