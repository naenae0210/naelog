Why doesn't 70B fit on one A100: GPU memory and quantization

Getting vllm serve to run is one thing; holding up as a service is another. Part 1 covers the first hurdle: calculating GPU memory, and quantization to shrink it.

This part asks one question: "Does this model fit on this GPU, and if it does, how many users' worth of room is left?" Most OOM (out of memory) errors happen when a model is launched without answering that question in numbers.

  1. Memory: split GPU memory into three parts (weights, KV cache, overhead) and calculate each
  2. Quantization: store numbers in fewer bits to save memory, and pick the right method per GPU
  3. Calculator: change the conditions and see exactly where OOM happens
  4. Cases: apply it to two situations that come up all the time

By the end you can explain "why 70B in BF16 does not fit on one A100" with a single multiplication. Unfamiliar abbreviations are in the glossary at the bottom.

GPU memory and model size

VRAM splits into three parts: weights, KV cache, and everything else (overhead). If you only calculate the first, you will be wrong.

In plain words · GPU memory is a desk

Think of GPU memory (VRAM) as a desk. Three things have to fit on it.

PartAnalogyWhat it does
WeightsA thick encyclopediaWhat the model has learned
KV cacheA conversation notepadSpace to write down the conversation so far
OverheadPens and a desk lampOdds and ends the program needs to run (2 to 4GB)

If the desk is too small, the encyclopedia does not fit (loading OOM). If the encyclopedia fits but there is no room for notepads, you cannot take any users (not enough KV).

Weights: parameter count × bytes per parameter

Weight memory = parameter count × bytes per parameter
ModelBF16 (2B)FP8 / INT8 (1B)INT4 (≈0.55B, with scales)

70B140 GB70 GB38.5 GB

"70B" means the model has 70 billion parameters (numbers it learned), and the 2B and 1B in the table header are the bytes one parameter takes. So 70B in BF16 is 70 billion × 2 bytes = 140GB, 140GB of weights alone. It never fits on a single 80GB card. It is not a misconfiguration; the arithmetic simply does not work, and this is the most common OOM there is.

KV cache: grows with concurrent requests and context length

To understand the KV cache, you first need to know a little about how the model is built. ChatGPT, Llama, Claude, Qwen and almost every LLM today use an architecture called the Transformer. The T in GPT is Transformer (Generative Pre-trained Transformer), and it first appeared in Google's 2017 paper "Attention Is All You Need".

A Transformer is dozens of identical layers stacked on top of each other. Llama 3.1 70B has 80. A token climbs from the bottom layer up, understood more deeply at each step, and the top layer picks the next token. Each layer uses attention to look at which earlier tokens to refer to, and feed-forward to process what it found. Attention works like looking things up in a library: every token produces three values.

ValueIn a libraryRole
QueryThe question I am asking"Right now I need this kind of information"
KeyThe label on a book's spine"This is what I contain"
ValueThe book's actual contentThe information you take once you find it

In "Chulsoo bought an apple. He…", when processing "He", matching the Query of "He" against the Keys of earlier tokens shows "Chulsoo" fits best. So the model takes Chulsoo's Value and understands "He = Chulsoo".

In other words, every new token needs the Keys and Values of all earlier tokens. Recomputing them each time would be wasteful, so the Transformer stores the Key and Value of every processed token in every layer and reuses them. That storage is the KV cache, the conversation notepad in the analogy above. Each of the 80 layers makes its own Keys and Values, which is why the formula below multiplies by the number of layers. And the longer the conversation, the thicker the notepad; the more users, the more notepads, so the total grows with length and user count.

KV per token = 2(K,V) × layers × KV heads × head dim × bytes

For Llama 3.1 70B (80 layers, 8 KV heads, head dim 128, BF16) that is 2×80×8×128×2 = 327,680 B per token, about 0.33MB.

70B, BF16 KV1 request16 concurrent64 concurrent
4K context1.3 GB21 GB86 GB
8K context2.7 GB43 GB172 GB
32K context10.7 GB172 GB687 GB

One 8K conversation is 2.7GB, but 64 people at once is 172GB. Even if the weights just barely fit, there is no service without room for the notepads. Put the other way: securing enough KV space is what concurrency is.

Overhead: the 2 to 4GB people forget

  • CUDA context: 0.5 to 1GB the moment a process grabs the GPU
  • Activations: intermediate tensors during prefill. Larger the longer the prompt processed at once
  • CUDA graph: graphs vLLM captures ahead of time for decode speed, hundreds of MB to a few GB
  • Other processes: an embedding server or Jupyter kernel on the same GPU. Check nvidia-smi first

Quantization

A technique that represents weights (and, if needed, activations and KV) in fewer bits to cut memory and bandwidth. You choose based on three things: GPU generation, how much quality loss you can accept, and what the serving engine supports.

In plain words · Quantization is photo compression

Compress a high-resolution photo to JPG and the file shrinks a lot while looking almost the same. Quantization is the same idea: store each number in 8 or 4 bits instead of 16, and a 70B model shrinks from 140GB to 70GB, or about 38.5GB.

But a compressed photo is not the original, and the more you shrink it the more the detail blurs. So the GPU generation decides which formats you can use, and real work questions decide how far you can shrink.

MethodBitsWhat it shrinksQualityGPUs
BF16 / FP1616BaselineOriginalAll
FP8 (W8A8)8Weights and activations, compute in FP8 tooNearly losslessAda (L40S, 4090), Hopper (H100/H200), Blackwell
INT8 W8A8 (SmoothQuant)8Weights and activationsNearly losslessAmpere (A100, A6000)
AWQ / GPTQ (W4A16)4Weights only, compute in FP16Some loss, shows first in math and codeAll, fast with Marlin kernels
NVFP4 / MXFP44Weights and activationsDepends on the calibration recipeBlackwell (B200)
GGUF (Q4_K_M etc.)2~8WeightsVaries by levelFor llama.cpp and Ollama. Not recommended for large-scale vLLM serving

How to choose

  1. If it fits in BF16 with plenty of KV, do not quantize. Quality validation costs nothing.
  2. On Hopper or Ada, start with FP8. Half the memory, faster compute, and almost no quality loss.
  3. On Ampere, INT8 W8A8 or AWQ INT4. The A100 has no FP8 tensor cores, so an FP8 checkpoint only saves memory, with no compute gain.
  4. If it still does not fit, INT4. Always compare it against BF16 on a set of real work questions.
  5. If concurrency is the problem, FP8 KV cache. The same memory holds twice as many KV tokens.
A common mistake

Quantization is not "a smaller model"; it is "an approximation of the same model". 70B INT4 is usually better than 32B BF16, but long-context reasoning and numerical calculation have to be checked directly on your own work data.

Back to real cases

70B on a single A100 80GB, and it OOMs

The math: BF16 weights are 140GB, usable memory is 80 × 0.9 = 72GB. You get CUDA out of memory while loading the weights. It is not a configuration problem; it is an arithmetic problem.

Switching to FP8 on an H100 80GB still gives 70GB of weights plus about 3GB of overhead, which goes over or nearly fills 72GB, and you get No available memory for the cache blocks. "The weights fit" and "the service works" are different things.

Options

  • Stay on one A100: AWQ INT4 (about 38.5GB) leaves about 30GB of KV → 11 concurrent at 8K; if FP8 KV is not supported, that is as far as it goes
  • Two A100s, TP=2: INT8 W8A8 (35GB per card) leaves about 68GB of KV in total → around 25 concurrent at 8K
  • Two H100s, TP=2: FP8 weights + FP8 KV → 50+ concurrent at 8K with minimal quality loss

To sum up, memory math, quantization, GPU generation (part 2) and concurrency (part 3) all connect into one calculation. Ask in order "does the encyclopedia fit on the desk → how many people's notepads fit" and you know which GPU and which format to use.

Which quantization should I use?

  • You have H100 or L40S: FP8. Hardly anything to think about
  • You only have A100 or A6000: AWQ INT4 (Marlin kernels) if memory is tight, INT8 W8A8 if there is room
  • 24GB cards like the RTX 4090: 70B does not fit on one card even in INT4. Even two cards with TP leave almost no KV, so no real service. 32B INT4 or 8B-class models are the realistic range
  • Always: decide after comparing 100 to 200 work questions side by side against BF16. A small gap on public benchmarks can still fall apart in a specific domain
