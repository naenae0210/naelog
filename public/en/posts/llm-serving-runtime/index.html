CUDA and GPU drivers

Running a model on a GPU takes several layers of software between the program and the GPU. Knowing what those layers are and how they connect clears up most installation errors.

What CUDA is

CUDA (Compute Unified Device Architecture) is NVIDIA's "way of giving work to the GPU". GPUs started as devices for drawing game graphics, but inside they hold thousands of small workers doing simple calculations at once, which suits work that repeats the same calculation enormously, like matrix multiplication, exactly what AI models do. CUDA is the way to give those workers jobs other than drawing. It only runs on NVIDIA GPUs; AMD uses a separate stack called ROCm.

CUDA is not one program; it is a bundle of parts.

PartExampleWhat it does
LanguageCUDA C++Syntax for writing functions (kernels) that run on the GPU
CompilernvccTurns that code into machine code the GPU reads

Among the libraries, cuBLAS handles matrix multiplication, where most LLM compute runs. cuDNN is a collection of deep learning operations, and NCCL ("nickel") is the library GPUs use to exchange data, called at every layer when you run tensor parallel across two GPUs.

PyTorch and vLLM write CUDA for you

Adding two arrays directly in CUDA looks like this.

// The function that runs on the GPU (kernel). Each worker takes one number
    __global__ void add(float* a, float* b, float* c, int n) {
        int i = blockIdx.x * blockDim.x + threadIdx.x;  // which worker am I
        if (i < n) c[i] = a[i] + b[i];
    }

    int main() {
        cudaMalloc(&a, n * 4);  cudaMalloc(&b, n * 4);  cudaMalloc(&c, n * 4);  // grab GPU memory
        cudaMemcpy(a, host_a, n * 4, cudaMemcpyHostToDevice);  // copy CPU → GPU
        cudaMemcpy(b, host_b, n * 4, cudaMemcpyHostToDevice);

        add<<<n / 256, 256>>>(a, b, c, n);   // launch many teams of 256 workers

        cudaMemcpy(host_c, c, n * 4, cudaMemcpyDeviceToHost);  // results GPU → CPU
        cudaFree(a); cudaFree(b); cudaFree(c);   // give the memory back
    }

Even one addition means handling allocation, copying, splitting work across workers, fetching results and freeing memory yourself. In PyTorch the same thing is one line.

import torch
    a = torch.randn(n, device="cuda")   # make an array on the GPU
    b = torch.randn(n, device="cuda")
    c = a + b                           # done

Behind a + b, PyTorch does the equivalent of the CUDA code above for you: it allocates memory, picks a prebuilt addition kernel, decides how many workers and launches it. For a matrix multiplication a @ b it calls cuBLAS internally. vLLM sits one level higher: without writing any PyTorch, one line, vllm serve model-name, builds the model in PyTorch and runs it whenever requests arrive.

How one request travels down to the GPU

When a user sends "Hi?", the instructions go down through five layers and the result comes back up.

User → ① vLLM → ② PyTorch → ③ CUDA runtime and libraries → ④ GPU driver → ⑤ GPU
StepPurposeWhat it does
① vLLMServe many guests efficientlyReceives the HTTP request → turns "Hi?" into token IDs (e.g. [52, 1031, 30]) → the scheduler batches it with other requests → assigns KV cache blocks → asks PyTorch to "run the model once on this batch". Queue, KV usage, preemption and other operational metrics all come from here
② PyTorchTranslate the model math into a list of GPU jobsFollows model code defined as "80 layers, attention and feed-forward in each" and turns matrix multiplies, softmax, normalization and so on into GPU jobs one by one. Tracks which GPU memory each tensor lives in
③ CUDA runtime and librariesRun this calculation as fast as possible on this GPUFor a "4096×8192 matrix multiply", cuBLAS picks the fastest method for this GPU generation and size (A100 and H100 choose differently). Queues kernel launches in order on a stream. Allocates and frees GPU memory
④ GPU driverInterpreter between the OS and the hardwareTurns CUDA commands into signals the hardware understands and puts them in the GPU command queue. Does the last compile of kernels to this GPU's machine code if needed. When several programs share one GPU, it orders them and keeps their memory apart. Like needing a printer driver to use a printer
⑤ GPUThe actual computeThousands of cores inside the SMs run the kernels in parallel. Reads weights and KV from HBM and writes results. After all 80 layers you get "a score for each candidate next token"
⑥ Back upOne token to the userPicks one next token from the scores (sampling), and vLLM turns it into text and streams it out. Then repeats ② to ⑤ for every token. This is the decode covered below

In practice there is also a path straight from ① to ③. Where speed matters, vLLM skips PyTorch's built-in ops and calls its own CUDA kernels directly, such as PagedAttention, FlashAttention and Marlin for 4-bit models.

This flow also gives a sense of scale. A 70B model passes through 80 layers to make one token, with several kernels per layer, so hundreds to thousands of GPU jobs go down for a single token. Just the CPU issuing those commands one by one can slow things down, so vLLM records the command sequence once and replays it whole. That is the CUDA graph in the overhead list of part 1 and in the last loading step below.

Versions stack three layers deep

"CUDA version" shows up in three places, the driver, the runtime and the Toolkit, which is what makes it confusing. You only need to know what is installed where.

The "CUDA Version 12.8" in nvidia-smi is not the installed CUDA; it is the maximum version this driver supports. That is why a CUDA 12.4 container image runs fine on it. There is one rule to remember: the CUDA runtime version the program uses ≤ the maximum version the driver supports.

What the inside of a GPU looks like

Earlier we called the GPU "a factory with thousands of workers". To understand why inference runs at the speed it does, you need to know where this factory computes and where it keeps its materials. Take the H100 SXM as the example.

  • SM (Streaming Multiprocessor): the compute block inside a GPU. The H100 has 132. Each SM holds tensor cores dedicated to matrix multiplication, CUDA cores for general compute, and very fast but small registers and shared memory (SRAM).
  • L2 cache: a middle store shared by all SMs. At 50MB it is tiny next to the 140GB of 70B weights.
  • HBM: where the weights and KV cache from part 1 actually live. Large, but much farther away than the memory inside an SM.

The numbers on the right are the key. An H100 can multiply and add about 990 trillion times per second, but read only about 3.35 trillion bytes per second from HBM. In other words, it can compute about 300 times in the time it takes to fetch one byte. Any work that does not compute more than 300 times per byte read leaves the compute units idle, waiting on memory, however fast they are. The difference between prefill and decode in the next section comes exactly from this.

FlashAttention makes sense in this picture too. Computed naively, attention writes an intermediate result (a score table of tokens × tokens) to HBM and reads it back. FlashAttention splits the computation into small tiles and finishes them inside the SM's SRAM, writing only the result to HBM. The computation is the same, but cutting the slow HBM round trips makes it faster and uses less memory at long context.

Model loading and inference

One request goes through two stages with completely different characters: "read it all at once" (prefill) and "write one token at a time" (decode).

Loading

  1. Weights are read from disk (safetensors) and copied to the GPU. 70B BF16 means reading 140GB, so NVMe or network storage speed decides startup time
  2. With tensor parallel, each layer's matrices are split across the GPUs. The GPUs exchange results over NVLink/PCIe at every layer
  3. The engine measures peak activation memory with a dummy request (profiling)
  4. All remaining memory is reserved up front as KV cache blocks. That is why nvidia-smi shows 90% right after vLLM starts, and that is normal
  5. CUDA graphs are captured, then it starts accepting requests

Prefill and decode

Prefill reads the whole question sheet in one go; decode writes the answer one character at a time.

Seen through arithmetic intensity

Whether a task is bound by compute or by memory is judged by its arithmetic intensity: how many operations it does per byte read from memory. The H100 baseline from the previous section is about 300.

  • Decode, 1 request: making one token reads all the weights once and does one multiply-add per weight. Reading a 2-byte BF16 weight for 2 operations gives an intensity of about 1. Far below the baseline of 300, so the compute units spend over 99% of the time waiting on memory.
  • Decode, 64 requests in one batch: the same weights are read once and used for all 64 requests. Intensity rises to about 64, and efficiency improves by that much. This is how batching works.
  • Prefill, a 2,000-token prompt: the weights are read once and used for 2,000 tokens at once. Intensity is well past the baseline, and now compute is busy while memory has room to spare.

This one picture ties the three parts together. Part 1's quantization cuts the bytes to read and speeds up decode on the slope, batching moves the point to the right, and part 3's "throughput rises then flattens as concurrency grows" is the point reaching the baseline. Strictly speaking, attention has to read each request's own KV cache separately, so that part's intensity does not rise with batch size. That is why batching helps less when there are many long-context requests.

Decode is bound by memory bandwidth because every character means skimming the whole encyclopedia (weights) once. At batch size 1, making one token means reading all the weights from HBM once. Running 70B BF16 (140GB) on two H100s (6.7TB/s combined) gives a theoretical ceiling of about 48 tok/s. Make the encyclopedia half as thick with quantization and the ceiling nearly doubles.

And when several requests share one skim of the weights, the bandwidth cost is split among them. It is like putting many passengers on one bus, and it is how batching raises throughput.

vLLM

vLLM is several times faster than HuggingFace generate() because of techniques that use memory sparingly and scheduling that processes requests together.

  • PagedAttention: splits the KV cache into small blocks like OS pages (16 tokens by default) and allocates them only when needed. Older engines reserved a full maximum-length notepad per request, and since most conversations end short, a lot was wasted. Handing out only what is needed lets far more requests fit in the same memory
  • Continuous batching: instead of waiting for a whole batch to finish, every decode step removes finished requests and adds new ones. Like a bus where, at each stop, some get off and others get on
  • Prefix caching: requests that start with the same system prompt or the same RAG documents build that part of the KV once and share it
  • Chunked prefill: splits a long prompt's prefill into chunks and slots them between decode steps, so one long request does not freeze other users' token generation

How tensor parallel splits a model

70B BF16 (140GB) does not fit on one GPU, so it has to be split across several. Tensor parallel cuts each layer's large matrices vertically or horizontally and gives each GPU one slice. With 2 GPUs, for example, each computes half of the matrix multiply at the same time, and their partial results are added together. That combining step (all-reduce) is handled by NCCL and happens twice per layer, after attention and after the feed-forward block. With 80 layers that is 160 times per token.

So the path between GPUs matters. NVLink between H100s moves hundreds of GB per second, while cards connected only over PCIe are close to ten times slower, and communication eats into compute time. That is why "two H100s" can perform very differently under TP depending on whether they have NVLink. If the model fits on one card, it is better not to split it, which leads to part 3's "TP versus replicas".

How the settings connect to the memory math

# 70B on two H100s, FP8 weights + FP8 KV
    vllm serve meta-llama/Llama-3.1-70B-Instruct \
      --tensor-parallel-size 2 \          # split weights across 2 cards
      --quantization fp8 \                # 140GB → 70GB
      --kv-cache-dtype fp8 \              # 2x KV tokens
      --max-model-len 16384 \             # max length of one request
      --gpu-memory-utilization 0.90 \     # use up to 72GB per card
      --max-num-seqs 64                   # cap on requests running at once

Two lines to always check in the startup log:

GPU KV cache size: 437,200 tokens
    Maximum concurrency for 16,384 tokens per request: 26.68x

The second line means "if every request fills 16K, up to 26 at once". Real requests are usually shorter so more fit, but you design around this number.

Typical OOM messages at startup

CUDA out of memory. Tried to allocate ...: the weights themselves do not fit.
No available memory for the cache blocks: the weights fit but there is zero room for KV.
max seq len (131072) is larger than the maximum number of tokens that can be stored in KV cache: there is not enough KV for the model's default max length (128K). Lowering --max-model-len fixes it.
