How block, file and object storage differ: from the bottom of the disk to MinIO

All three end up on the same disks. The difference is how the data is cut up, what it is called, and who takes it out by which path. We follow that difference from the bottom of the disk up, one layer at a time.

2026.11.2320 min StorageFile SystemsS3MinIO

"Why do DBs live on EBS and photos on S3?" Answering that properly means going all the way down to how a disk stores data and how the operating system handles that disk. This post starts at the physical media and builds up one layer at a time: the OS, block, file, then object. By the end you can explain for yourself why each layer looks the way it does, and therefore what work it suits.

In plain words · Three warehouses

Imagine three kinds of warehouses that store the same goods.

  • Block storage: rents out empty shelf slots that only have numbers. The renter decides what goes where. The warehouse has no idea "what is in slot 37".
  • File storage: has a librarian who labels the shelves with folders and names. Ask for "cat.jpg in the photos folder" and you get it, and you can swap out a single page too.
  • Object storage: a parcel locker. You drop off a whole box and get a tracking number (key); to collect, you give the number and get the whole box back. In return, the locker is easy to run no matter how big it grows, and you can drop off and pick up from anywhere over the internet.

The same photo stored three ways

Let us start with the result. Here is how each of the three "knows" the same cat.jpg (about 2.4MB).

# Block: there is no concept of a "photo"
LBA 1048576 ~ 1049181  (606 blocks × 4KiB)  ← bytes are simply written in this range
# Only the file system on top knows that this is a photo or where it starts

# File: there is a path and a ledger
/data/photos/2026/cat.jpg
inode 1310722 · size 2481152 · owner kim · mode 0644
→ data blocks: 1048576-1049181

# Object: there is a bucket, a key, and an HTTP address
Bucket: photos   Key: 2026/cat.jpg
ETag: "9b2cf535f27731c974343645a3985328" · Content-Type: image/jpeg
GET https://s3.example.com/photos/2026/cat.jpg   # from anywhere, once authenticated

Block knows only numbers, file knows names and a ledger, and object knows names and a ledger plus "an address you can fetch from anywhere". Notice that the file's data block numbers (1048576-1049181) are the same numbers as on the block side. The file sits on top of blocks, and object storage in turn sits on files and blocks somewhere. To see why they stack this way, let us climb up from the very bottom.

At the bottom: disks only read and write in fixed sizes

Physical media know nothing about files or objects. They only read and write in fixed-size units. But those units and speeds differ by medium, and the layers above are designed around them.

HDD: waiting for the platter to come around

In an HDD, magnetized platters spin fast while a head moves across them, flipping the magnetic field to record 0s and 1s. The platter surface is divided into concentric tracks, and each track into pieces called sectors. A sector is the smallest unit read or written, traditionally 512 bytes and commonly 4KiB today.

HDDs are slow because of this mechanical motion. To read, the head first moves to the right track (seek), then waits until the right sector spins under it (rotational latency). A 7,200rpm disk takes about 8.3ms per revolution, so on average it waits half a turn, about 4.2ms. Add a few ms of seek and one random read takes close to 10ms, which limits random reads to roughly 100 to 200 per second. Sequential reads, continuing from where the head already is, just read along as the platter spins and are much faster.

This gap shaped the layers above for a long time. It is why file systems try to keep a file in contiguous blocks, and why DBs like appending changes to the end of a log file: turning random writes into sequential ones means the head moves less.

SSD: memory that cannot overwrite

An SSD stores charge trapped in the cells of NAND flash chips. With no moving parts there is no seek or rotation, and any location reads at nearly the same speed. But NAND has a tricky rule that HDDs did not.

  • The unit for reading and writing is a page (usually 4 to 16KiB).
  • The unit for erasing is a block, a group of hundreds of pages.
  • A page that already holds data cannot be overwritten in place. The whole block has to be erased before it can be written again.

So inside the SSD is controller software called the FTL (Flash Translation Layer). When a request comes in to "overwrite logical address 100", the FTL does not write in place; it writes to an empty new page and updates its address table to "100 is now that page". The old page is just marked invalid.

As invalid pages pile up, the FTL runs garbage collection (GC) in the background: it copies still-valid pages to another block and erases the old block whole to reclaim space. The disk ends up writing more than the user did, which is called write amplification. NAND cells can only be erased and written a limited number of times, so high write amplification wears an SSD out faster.

When the OS deletes a file, the SSD does not know. From outside, the SSD only knows "there is data at address N", not "that data is no longer needed". So when the OS sends a TRIM command saying "these addresses are now free", the FTL can skip moving those pages during GC, which helps both performance and lifespan.

"Block" appears twice

The NAND "block" (the erase unit, usually a few MiB) and the block in "block storage" (the read/write unit the OS sees, usually 4KiB) are words from completely different layers. The FTL translates between them, so the outside never needs to know NAND internals.

NVMe: an interface, not a medium

Even with the same NAND chips, SATA SSDs and NVMe SSDs differ a lot in speed. The difference is not the medium but how it connects to the computer. SATA was designed for HDDs, so it has a single command line (queue) that holds up to 32 commands. That was enough for an HDD with one head, but it bottlenecks an SSD that can read many places at once. NVMe sits directly on the PCIe bus and allows up to about 65 thousand queues, each holding about 65 thousand commands. Usually each CPU core gets its own queue, so cores put commands in at the same time without waiting on each other.

To get a rough feel, here are typical latencies side by side. They vary a lot by product and conditions, so look only at the orders of magnitude.

MediumOne random 4KiB readWhy about that much
HDD (7,200rpm)a few to 10msHead movement and waiting for rotation
SATA SSDabout 100μsNo mechanics, but one queue and an old protocol's overhead
NVMe SSDtens to 100μsDirect PCIe, per-core queues

In the end, everything shows up as LBAs

Whether HDD sectors or SSD pages, after the controller everything looks the same from outside: a long array of fixed-size slots starting at 0, and only two things to say, "read M blocks starting at LBA (Logical Block Address) N, write them". The HDD head position and the SSD's FTL table both hide behind this. The first gate on the way up from the physical media is always this block unit, and every layer from here on sits on these LBAs.

How the operating system handles the disk

When a program reads a file, it does not touch the disk directly. The OS puts several layers in between and splits the work among them. Following one Linux read() down makes clear where the boundary between block and file storage lies.

  1. System call: when a program calls read(), execution moves from user space into the kernel. Programs never touch the disk directly; they always ask the kernel.
  2. VFS (Virtual File System): Linux takes any file system, ext4, XFS, NFS and so on, through the same entrance. So programs can call open and read the same way whatever sits below.
  3. File system: translates "bytes 0 to 4,095 of this file" into "block at LBA 1,048,576". The ledger used for this translation is the inode we will see later.
  4. Page cache: the kernel keeps recently read and written disk content in spare memory. If the wanted block is already in memory, it is returned from here without going to the disk. That is why reading the same file a second time is much faster.
  5. Block layer: if it is not cached, an LBA read request is created. Nearby requests are merged and ordered for the device (the I/O scheduler) before going to the driver.
  6. Driver and device: the NVMe driver puts the request in the device's queue, the device sends the data to memory, and it travels back up into the program's buf.

Writes go to memory first; fsync gets them to disk

For writes, the page cache matters even more. write() usually just copies the data into the page cache, marks it "dirty" and returns right away. It actually reaches the disk later, when the kernel flushes in bulk. That makes writes fast, but if power is lost in between, data can vanish even though write() succeeded.

That is what fsync() is for. It means "wait until this file's changes are definitely on the disk". DBs write to a log file and call fsync() on every transaction commit because data they reported as saved must survive a power cut. That one fsync() is the moment that takes the full disk latency, so a DB's commit speed is ultimately bound to the write latency of the block device beneath it.

You can also bypass the page cache on purpose. Opening a file with O_DIRECT skips the kernel cache and talks to the device directly. DBs that manage their own cache sometimes use it to avoid holding the same data twice, once in their cache and once in the OS's.

Block storage: lending the LBAs as they are

Block storage lends a server the LBA array we just saw, almost as it is. No names, no folders, no permissions; this is all it understands.

# These are effectively the only commands a block device understands
READ  (LBA=1048576, count=8)   # read 8 blocks from block 1048576 = 32KiB
WRITE (LBA=1048576, count=8, data)

An SSD plugged into a server, an EBS volume attached in the cloud, a volume (LUN) a storage array hands over the network: to the server, they all appear as an empty block device like /dev/nvme1n1. You cannot put files on it until the server's OS creates a file system on top (formatting), and only then do folders and files exist. In terms of the figure above, block storage lends only "below the block layer", and the file system and page cache above it are handled by the server that borrows it.

# 1) List attached block devices
$ lsblk
NAME        SIZE TYPE MOUNTPOINT
nvme0n1      50G disk
└─nvme0n1p1  50G part /
nvme1n1     500G disk              # newly attached volume. No names or folders yet

# 2) Create a file system on it (block → file layer)
$ sudo mkfs.xfs /dev/nvme1n1
$ sudo mount /dev/nvme1n1 /data
$ df -h /data                      # now you can write files under /data

Block storage is fast because it knows nothing. There is no layer to parse paths or check permissions, so small, frequent requests like "change exactly these 4KiB" take the shortest path. A DB keeps rewriting pages of, say, 8KiB in place inside its data files and waits on fsync() at every commit. That is why DBs and VM disks sit on block storage. The metrics to watch are operations per second (IOPS) and per-request latency.

One volume, one server

A file system's ledger and page cache live in the memory of the server that mounted the volume. If two servers each mount ext4 on the same block device and write at once, they overwrite each other's cache and ledger changes without knowing and the file system breaks. Sharing needs a cluster file system or special features like EBS Multi-Attach.

File storage: a ledger of names on top of numbers

A file system (ext4, XFS, NTFS, APFS and so on) uses part of the block device as a ledger that records whose data sits in the remaining blocks. The ledger has three key parts.

ComponentWhat it does
inodeThe info card for one file: size, owner, permissions, modification time and the list of block numbers holding the data. The file name is not here
DirectoryA special file holding a "name → inode number" table. photos/ is just a list of name tags inside it
JournalA log that records ledger changes first so the ledger survives a power cut

It matters that names live in directories, not in inodes. That is why opening /data/photos/2026/cat.jpg makes the file system walk down the path one step at a time.

This structure lets the file system offer features people find convenient: find things by path, change a few bytes in the middle of a file, and rename a folder instantly by editing one line of the ledger. Programs use these features through system calls like open, read, write, lseek and close; this set of rules is POSIX, and most programs are built on it.

# Show a file's inode info
$ stat /data/photos/2026/cat.jpg
  Size: 2481152    Blocks: 4848   IO Block: 4096   regular file
 Inode: 1310722    Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/  kim)

# Change a few bytes in the middle of a file: possible because it is a file system
$ printf 'XY' | dd of=cat.jpg bs=1 seek=100 conv=notrunc

For many servers to see one folder: NAS

A local file system keeps its ledger and cache in one server's memory, so only that server uses it. For many servers to see the same folder, the file system lives in one place (a file server, NAS) and is shared over network protocols like NFS or SMB. Clients do not handle blocks or ledgers directly; they ask across the network to "read this file, list this folder". Locks, permissions and cache consistency are coordinated in this protocol layer, so many servers can write safely at once, but that coordination and the round trips add latency.

Recall the path lookup figure and it becomes clear why working with millions of small files is unusually slow on NFS: every file's name lookup and attribute check becomes a network round trip. For the same reason, growing one file system to billions of files across regions is hard and expensive. Every server has to keep one ledger and one lock state in sync in real time.

Object storage: give up folders, gain scale

What made file systems hard to grow was, in the end, the ledger. Keeping a directory tree, partial updates and locks all intact while growing to thousands of servers is hard. Object storage boldly gives up all three.

  • Flat names instead of a tree: data is stored as "key → object" inside a big container called a bucket. The key is just a string.
  • Whole objects instead of partial updates: objects are written whole and read whole. Range reads work, but changing part means overwriting with a new object.
  • HTTP instead of locks and system calls: you use it with HTTP requests like PUT, GET and DELETE. It does not go through the OS file system layer.

The / in the key 2026/cat.jpg is not a folder separator; it is just a character in the string. What looks like folders in the console is the listing cut up with prefix=2026/ and delimiter=/. So there is no "rename folder"; turning 2026/ into 2025/ means copying and deleting every object under it, something a file system does with one line of its ledger.

In return, with no tree to manage, keys can easily be hashed and spread across huge numbers of servers. Which server holds an object can be computed from the key alone, and there is no single ledger everyone has to keep in sync. That is how object storage grows to petabytes and billions of objects while staying the cheapest per GB.

# Upload and download with the CLI (same commands for AWS S3 or MinIO, only the endpoint changes)
$ aws s3 cp cat.jpg s3://photos/2026/cat.jpg --endpoint-url http://localhost:9000

# What actually goes over the wire is an ordinary HTTP request
PUT /photos/2026/cat.jpg HTTP/1.1
Host: localhost:9000
Content-Type: image/jpeg
x-amz-meta-owner: kim                 # user-defined metadata
Authorization: AWS4-HMAC-SHA256 ...   # authenticated by signature

# Python (boto3): a download link usable without login for 10 minutes
import boto3
s3 = boto3.client("s3", endpoint_url="http://localhost:9000")
url = s3.generate_presigned_url("get_object",
      Params={"Bucket": "photos", "Key": "2026/cat.jpg"}, ExpiresIn=600)

The price is clear too. Every request goes through an HTTP round trip and distributed software, so single-request latency is a few to tens of ms, the longest of the three. That is why object storage suits data that is "written once, read many times, large in volume and taken out from many places". For such data it has versioning (keep old versions when overwritten), lifecycle rules (move old data to cheaper classes automatically), Object Lock (no deletion for a set period) and multipart upload (split large files into parts uploaded in parallel).

What MinIO actually does on the disks

Object storage also ends up on disks. So how is it different from "putting files on a disk"? Following MinIO's internals makes it clear. Say you build a cluster of 4 servers with 4 disks each, 16 disks in total.

  1. Deciding where: disks are grouped into erasure sets (say, 16 per set). The key 2026/cat.jpg is hashed to pick the set, so there is no central ledger to look up.
  2. Splitting and making parity: the data is split into 12 parts, and 4 parity parts are computed from them (erasure coding). Parity is "spare information for recomputing lost parts".
  3. Writing on each disk: each disk's XFS stores something like /mnt/disk1/photos/2026/cat.jpg/xl.meta (metadata, versions, checksums) and .../part.1 (the part this disk holds). The name is cat.jpg, but it is a folder holding just one part.
  4. Reading: the parts are gathered, checked against checksums, recovered from parity if needed and joined back together. Damaged parts are rewritten in the background (healing).

In other words, object storage is a distributed system that uses file systems as parts. That is why MinIO's documentation says not to combine disks with RAID or NFS, but to put XFS on each disk separately and hand them over as they are: MinIO does the recovery and distribution itself.

Note · Where MinIO community edition stands (as of November 2026)

MinIO was widely used because a single Go binary could run S3-compatible storage, but in 2025 the community edition's console was cut back and Docker image releases stopped, and in 2026 its GitHub repository was archived. The company focuses on its commercial product AIStor, so it is hard to recommend as the default for new production systems. Alternatives include Ceph RGW (large scale, hard to operate), SeaweedFS (huge numbers of small files), Garage (small self-hosting), and cloud S3, GCS, Azure Blob and Cloudflare R2. They all speak the same S3 API, so if your code sticks to standard S3 calls, switching means changing only the endpoint and credentials. Check each product's latest status before adopting it.

The three branches in one picture

Now we can redraw the opening picture. Up to the physical media and LBAs the three share one path, and they split depending on what sits on top.

The higher you go in the picture, the thicker the software you pass through. Block passes LBAs almost directly to the server OS, file adds a ledger and a sharing protocol on top, and object goes through distributed software and HTTP as well. So latency grows in the order block < file < object, while sharing and scaling get easier in the same order. Almost every cell of the comparison table below follows from that one sentence.

What to choose

Once you know the reasons, choosing is simple. Ask three questions.

What to watch when operating each also follows directly from its nature.

Watch forWhy
BlockPick tiers by IOPS and latency, replicate snapshots to another region regularly, turn on volume encryption by defaultA DB's commit speed is bound to this device's write latency, and you pay for the provisioned capacity
FileReview throughput tiers, not just capacity; manage network access control and POSIX permissions together; pair snapshots with file-level backupsAs concurrent access grows, keeping the ledger and locks in sync becomes the bottleneck
ObjectKeep buckets private by default, stick to one permission method (IAM, bucket policies or ACLs), turn on versioning and lifecycle rulesIt is reachable from anywhere on the internet, so a public setting mistake is a leak, and as data piles up, storage class design drives cost

It is also worth remembering that object storage is an independent service outside the VPC, not inside it. When servers inside the VPC access it, choose between a public endpoint over the internet and a VPC endpoint (PrivateLink) on the internal network, and do not assume security groups alone control access.

Back to real cases

A photo sharing service

  • Block: PostgreSQL with users, posts and like counts. It rewrites small rows nonstop and calls fsync() at every commit, so it lives on fast block volumes (EBS gp3, local NVMe).
  • Object: original photos and thumbnails. Rarely changed once uploaded, read worldwide. Keep them on S3 behind a CDN, and store only the key (2026/11/u42/abc.jpg) in the DB. For uploads, the app server issues a presigned URL and the browser uploads straight to S3, so the app server does not relay large files.
  • File: config files and build artifacts are ordinary files on the server's local disk.

A common mistake is putting photos in a DB BLOB column or on the app server's local disk at /uploads. The moment you scale to two servers, you hit "which server did I upload that to?" A local disk is block storage, and block storage belongs to one server.

Training models on a GPU cluster

  • Object: keep the original dataset (tens of TB) and checkpoints on cheap, safe object storage.
  • Block: right before training, download data in shards to each node's local NVMe so the GPUs read from the fastest layer.
  • File: when many nodes need to see the same code and small configs, use a shared file system like Lustre or NFS.

Reading millions of small images as individual objects makes the HTTP round trip on every request the bottleneck. Store them in shards of hundreds of MB (tar, WebDataset, Parquet and so on) to actually use object storage's high throughput: single requests are slow, but fetching big chunks in parallel gives very high total throughput.

"Wouldn't it be easier to run MinIO on NFS?"

With a NAS already in place, handing MinIO a single NFS-mounted folder looks easy, but it is not a recommended setup. MinIO is designed to manage per-disk parts, checksums and recovery itself; if NFS handles caching and locking separately in between, consistency can break. And if that one NFS server dies, everything stops, so the benefit of distribution disappears too. Layers make sense when stacked from the bottom up, and the standard is to run object storage on XFS on each server's local disks (block).

Common misconceptions

MisconceptionReality
"write() succeeded, so it is on disk"Usually it is only in the page cache. Data that must survive a power cut needs fsync() as well.
"Overwrites are free on an SSD"NAND cannot overwrite in place, so the FTL writes new pages and cleans up later with GC. The more random writes, the higher the write amplification and the shorter the lifespan.
"S3 has folders"The console just cuts keys at / to make them look like folders. An empty "folder" is faked with a zero-byte object named 2026/.
"Mount it with s3fs and it becomes a file system"It only imitates one. Changing part of a file re-uploads the whole object behind the scenes, and locks and renames are limited or slow. Use it for read-mostly work only.
"Object storage is slow"Single-request latency is long, but with many parallel requests total throughput is very high. Downloading a large file in many parts at once can reach tens of GB/s.
"Read right after writing and you get the old version"That is old S3. AWS S3 has guaranteed strong read-after-write consistency since December 2020. Compatible products may differ, so check.
"We have RAID or erasure coding, so no backups needed"They only protect against disk failure. Accidental deletes and ransomware get replicated just the same. You need versioning, Object Lock and backups in another location.

Summary

  • Physical media only read and write in fixed sizes. HDDs are slow at random access because of the head and rotation, SSDs cannot overwrite so the FTL remaps addresses as it writes, and NVMe uses per-core queues for parallelism. From outside, all of them look like LBAs.
  • The OS goes through system calls, VFS, the file system, the page cache and the block layer to produce LBA commands. write() lands in memory; only fsync() makes it stick on disk.
  • Lend the LBAs as they are and you have block storage; add a ledger of names and share it and you have file storage; replace the ledger with flat keys, wrap it in distributed software and expose it over HTTP and you have object storage.
  • The higher the layer, the longer the latency and the easier sharing and scaling. Put DBs and VMs on block, folders edited together on file, and data you pile up and take out from many places on object.
