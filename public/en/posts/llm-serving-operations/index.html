What breaks first at 100 users: metrics and concurrent requests

Being fast for one user is different from holding up for a hundred. Part 3 covers reading the metrics and designing for concurrent requests.

Part 1: for a model to fit, weights + KV cache + overhead have to fit in GPU memory. The room for KV cache is how many people you can serve at once.

Part 2: answers are produced one character (token) at a time (decode), and every token means reading all the weights, so memory speed is the bottleneck. That is why batching, putting many requests on one bus, raises efficiency, and vLLM runs that bus.

This part asks "once people actually start using it, where does it slow down, and how many can it handle?"

  1. Performance metrics: the GPU utilization trap, response time (TTFT, TPOT, E2E), throughput
  2. Handling concurrent requests: the order things break as users grow, and how to size capacity
  3. A case: going from 10 users to 100

GPU Utilization, Inference Latency, Throughput

GPU utilization hides more than you think

GPU-Util 100% in nvidia-smi only means "at least one kernel was running during the sampling window", not that the SMs were full. Lights being on in a factory does not mean every worker is busy. Decode-heavy load often shows 100% Util while using only 20 to 30% of the compute units. The real picture is DCGM's SM Activity and DRAM Activity (bandwidth use). 90% memory usage is not a load metric either; vLLM reserved it up front. Actual KV usage is vLLM's vllm:gpu_cache_usage_perc.

TPOT and ITL mean almost the same thing: the average gap between tokens is TPOT, and each individual gap is ITL. The three metrics connect like this. With TTFT 0.5s, TPOT 50ms and 200 output tokens, E2E is about 0.5 + 0.05 × 199 ≈ 10.5s.

People read at roughly 5 to 10 tokens per second, so for streaming chat a common target is TPOT under 100ms and TTFT under 1 to 2 seconds. Here you have to look at p95 and p99 (the 95th and 99th percentiles, the slowest 5% and 1%), not the average, to see the delays some users actually hit. Even with a fine average, a p95 of 10s means 1 in 20 people waits more than 10 seconds.

Throughput is traded against latency

Throughput is "tokens the whole GPU generates per second" (output tok/s) or "requests handled per second" (req/s). As concurrency rises, the cost of reading the weights is split across more requests, so total throughput goes up; but each step has more work, so each request's TPOT grows. Like a bus: more passengers means more carried per trip, but each stop takes longer. Past a certain point throughput barely moves and only latency grows, and just before that is the best operating point.

Handling concurrent requests

As users grow, things break in almost the same order every time.

  1. TPOT slowly grows: bigger batches make each step longer. Still in the normal range
  2. The KV cache fills and a queue forms: vllm:num_requests_waiting goes above 0. New requests wait until KV blocks free up, so TTFT shoots up
  3. Preemption: when running requests run out of KV, vLLM evicts some and later recomputes them from the start. Doing the same work twice drops throughput too. Check vllm:num_preemptions_total
  4. Timeouts: past the gateway's (nginx, Cloudflare etc.) wait limit you get 504. Users feel "the server is down"

Sizing concurrency: Little's law

Concurrent requests = requests per second × average time per request (s)

It is the same formula as "people in the shop = people arriving per minute × time each one stays". If 2 requests arrive per second and each answer takes 15 seconds on average, 30 are always running at once. Those 30 × average tokens per request must fit in the KV budget for it to run without a queue.

What to do

SymptomTry first
Not enough KV, queueingFP8 KV cache, smaller --max-model-len, quantize weights to free KV room, add GPUs (TP or replicas)
TTFT up from long RAG promptsPrefix caching, fewer retrieved documents or shorter chunks, chunked prefill
TPOT upCap the batch with --max-num-seqs, a smaller or quantized model, a GPU with more bandwidth
Repeated preemptionLower --max-num-seqs, free KV. Preemption is a signal that "taking a bit less is better"
Uneven load per userPer-user concurrency limits at the gateway, an output token cap (max_tokens)

TP and replicas serve different purposes. TP is for "a model that does not fit on one card"; if it fits, running several replicas on the same number of GPUs behind a load balancer usually gives better throughput because there is no GPU-to-GPU communication.

Back to a real case

Going from 10 users to 100

Assume two H100s, 70B FP8, and 4K tokens per request on average. With a KV budget of about 400,000 tokens, 4K requests top out at a little over 100 concurrent.

  1. 10 users: small batches, short TPOT, most GPU bandwidth wasted
  2. 50 users: throughput rises sharply and TPOT grows with it. Still feels fine
  3. 100 users + long RAG documents: KV limit reached, a queue forms, TTFT jumps from seconds to tens of seconds
  4. In that state, if some users attach 32K documents, one request takes the KV of eight 4K requests and preemption starts

So in operations you put four numbers on the dashboard, num_requests_waiting, gpu_cache_usage_perc, num_preemptions_total and TTFT p95, and use "the queue is no longer zero most of the time" as the trigger to scale up.
